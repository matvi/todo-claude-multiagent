## 1. Overview

A minimal, self-contained Todo web application intended as a **demo / reference
implementation**, not a production-scale system. A user can create todo items,
list them, mark them complete/incomplete, edit them, and delete them. There is
**no authentication** — the app is single-tenant and treats all todos as
belonging to one anonymous user. The stack is a React SPA (Vite) talking over
REST to a .NET 10 Web API, which persists to Azure Database for PostgreSQL. All
compute runs on Azure Container Apps.

The guiding principle throughout: **keep it simple**. Do not add auth, multi-
tenancy, message queues, caching layers, or microservices. One frontend
container, one backend container, one database.

### Core user stories

- As a user, I can **create** a todo with a required title and an optional
  description.
- As a user, I can **view a list** of all todos, newest first, showing title,
  description, completed state, and created date.
- As a user, I can **toggle a todo's completed** state.
- As a user, I can **edit** a todo's title and/or description.
- As a user, I can **delete** a todo.

## 2. Data model / Database schema

Single table. PostgreSQL. Primary key is a UUID generated by the application
(EF Core / .NET `Guid`), which avoids depending on a Postgres extension.

### Table: `todos`

| Column        | Type                        | Constraints / Notes                                  |
|---------------|-----------------------------|------------------------------------------------------|
| `id`          | `uuid`                      | Primary key. Generated by the API (`Guid.NewGuid()`).|
| `title`       | `varchar(200)`              | `NOT NULL`. Non-empty (validated in API).            |
| `description` | `varchar(2000)`             | `NULL` allowed.                                      |
| `is_completed`| `boolean`                   | `NOT NULL`, default `false`.                         |
| `created_at`  | `timestamptz`               | `NOT NULL`, default `now()`. Set on insert.          |
| `updated_at`  | `timestamptz`               | `NOT NULL`, default `now()`. Updated on every write. |

### DDL (reference — created via EF Core migration, see §3.4)

```sql
CREATE TABLE todos (
    id           uuid          PRIMARY KEY,
    title        varchar(200)  NOT NULL,
    description  varchar(2000) NULL,
    is_completed boolean       NOT NULL DEFAULT false,
    created_at   timestamptz   NOT NULL DEFAULT now(),
    updated_at   timestamptz   NOT NULL DEFAULT now()
);

CREATE INDEX ix_todos_created_at ON todos (created_at DESC);
```

Notes:
- The schema is owned by **EF Core migrations** (code-first). The DDL above is
  the expected output; do not hand-maintain SQL. The engineer must generate an
  initial migration named `InitialCreate`.
- `updated_at` is set by application code on create and update (do not rely on a
  DB trigger — keep it simple).

## 3. Backend — .NET 10 Web API

### 3.1 Technology choices

- **.NET 10**, ASP.NET Core Web API.
- **Controllers** (not Minimal APIs) — clearer structure for the engineer and
  tester agents, and easier to unit/integration test.
- **EF Core 10** with the **Npgsql.EntityFrameworkCore.PostgreSQL** provider.
- **Swagger / OpenAPI** enabled in Development for manual exploration
  (`Microsoft.AspNetCore.OpenApi` + Swashbuckle).
- Nullable reference types enabled; implicit usings enabled.

### 3.3 Configuration

- Connection string key: `ConnectionStrings:TodoDb`.
- Read from configuration/environment. In Azure it is injected as an env var
  `ConnectionStrings__TodoDb` from a Container Apps secret (see §5.5).
- CORS: a named policy `frontend` that allows the frontend origin. Allowed
  origins come from config key `Cors:AllowedOrigins` (array of strings).
  - Local dev default: `http://localhost:5173`.
  - Azure: the frontend Container App's FQDN (e.g.
    `https://todo-web.<env-hash>.<region>.azurecontainerapps.io`).
- A `GET /health` endpoint returns `200 OK` with body `{ "status": "ok" }`,
  used by Container Apps health probes. Do not gate it behind CORS/auth.

### 3.4 EF Core / migrations

- `TodoDbContext` exposes `DbSet<Todo> Todos`.
- Configure entity in `OnModelCreating` (column types, max lengths, index on
  `created_at DESC`).
- Apply migrations automatically at startup for this demo:
  `db.Database.Migrate()` in `Program.cs` (guard with a try/log; acceptable for
  a demo, noted as a simplification over a separate migration step).
- Engineer must run `dotnet ef migrations add InitialCreate` and commit the
  generated `Migrations/` folder.

### 3.5 API surface

Base path: `/api/todos`. All request/response bodies are JSON. JSON property
naming is **camelCase** (ASP.NET Core default).

#### DTO shapes

`TodoResponse` (returned by all read/write endpoints):
```json
{
  "id": "b3f1c2e4-...-uuid",
  "title": "Buy milk",
  "description": "2%, from the corner store",
  "isCompleted": false,
  "createdAt": "2026-07-23T10:15:30Z",
  "updatedAt": "2026-07-23T10:15:30Z"
}
```

`CreateTodoRequest`:
```json
{ "title": "Buy milk", "description": "2%, from the corner store" }
```
- `title`: required, 1–200 chars after trim.
- `description`: optional, max 2000 chars, may be null/omitted.

`UpdateTodoRequest` (full update of the mutable fields):
```json
{ "title": "Buy oat milk", "description": null, "isCompleted": true }
```
- `title`: required, 1–200 chars.
- `description`: optional, max 2000 chars, nullable.
- `isCompleted`: required boolean.

Validation is enforced via data annotations + automatic model validation
(returns RFC 7807 `ValidationProblemDetails` on failure).

#### Endpoints

| Method | Path              | Body                 | Success        | Notes                                   |
|--------|-------------------|----------------------|----------------|-----------------------------------------|
| GET    | `/api/todos`      | —                    | `200` `TodoResponse[]` | Ordered by `createdAt` DESC.     |
| GET    | `/api/todos/{id}` | —                    | `200` `TodoResponse`   | `404` if not found.              |
| POST   | `/api/todos`      | `CreateTodoRequest`  | `201` `TodoResponse`   | `Location` header set. `400` on validation error. |
| PUT    | `/api/todos/{id}` | `UpdateTodoRequest`  | `200` `TodoResponse`   | `404` if not found. `400` on validation error. |
| DELETE | `/api/todos/{id}` | —                    | `204`          | `404` if not found.                      |
| GET    | `/health`         | —                    | `200`          | Liveness/readiness probe.                |

- `{id}` is a `Guid`; malformed ids return `400`.
- Errors use `ProblemDetails` (default ASP.NET Core behavior).
- No pagination (dataset is small by design). Document as an out-of-scope
  simplification (§8).

### 3.6 Backend Dockerfile

Multi-stage build at `backend/src/TodoApi/Dockerfile`, built with the **backend
build context set to `backend/`** so the `.sln`/project layout resolves:

```dockerfile

COPY src/TodoApi/TodoApi.csproj src/TodoApi/
RUN dotnet restore src/TodoApi/TodoApi.csproj

RUN dotnet publish src/TodoApi/TodoApi.csproj -c Release -o /app

```

- Container listens on port **8080** (Container Apps ingress target port).
- If the exact `mcr.microsoft.com/dotnet/*:10.0` tags are unavailable at build
  time, use the closest available `10.0-*` tag; note the substitution in
  `changes.md`.

## 4. Frontend — React SPA (Vite)

### 4.1 Technology choices

- **Vite + React 18 + TypeScript** (plain React, no Next.js/Remix).
- **State management: React built-in only** — `useState` + `useEffect`, plus a
  small custom hook `useTodos` that owns the list state and API calls. No Redux,
  Zustand, or React Query — overkill for this app.
- **HTTP: native `fetch`** wrapped in a thin `api.ts` client. No axios.
- Styling: a single plain CSS file (`index.css`). No UI component library.
- The API base URL is read from a Vite env var `VITE_API_BASE_URL`
  (e.g. `http://localhost:8080` locally, backend Container App FQDN in Azure).

### 4.2 Project structure

Lives under `/frontend`. Exact names:

```
frontend/
  index.html
  package.json
  vite.config.ts
  tsconfig.json
  .env.development            # VITE_API_BASE_URL=http://localhost:8080
  nginx.conf                 # SPA fallback for container serving
  Dockerfile
  src/
    main.tsx
    App.tsx
    index.css
    types.ts                 # Todo type + request types
    api.ts                   # fetch wrapper: listTodos, createTodo, updateTodo, deleteTodo
    hooks/
      useTodos.ts            # list state + CRUD orchestration
    components/
      TodoForm.tsx           # create form (title + optional description)
      TodoList.tsx           # renders TodoItem[]
      TodoItem.tsx           # row: checkbox complete, inline edit, delete button
```

### 4.3 Component / data-flow design

- `App.tsx` calls `useTodos()` and renders `TodoForm` + `TodoList`.
- `useTodos` holds `todos`, `loading`, `error` and exposes `create`,
  `update`, `toggleComplete`, `remove`, `reload`. Each mutation calls the API
  then updates local state optimistically-or-on-success (engineer's choice;
  on-success is simplest and preferred).
- `api.ts` functions map 1:1 to the REST endpoints in §3.5 and throw on non-2xx
  so the hook can surface an error message.
- `TodoItem` supports inline editing of title/description and a checkbox that
  triggers `toggleComplete` (which issues a `PUT` with the flipped
  `isCompleted`).

### 4.4 Frontend Dockerfile + serving

Build the static bundle and serve it with nginx. `nginx.conf` must include SPA
history fallback (`try_files $uri /index.html;`). Container listens on port
**8080** to match Container Apps conventions.

```dockerfile
# build
FROM node:22-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
# VITE_API_BASE_URL is baked at build time; pass via --build-arg
ARG VITE_API_BASE_URL
ENV VITE_API_BASE_URL=$VITE_API_BASE_URL
RUN npm run build

# runtime
FROM nginx:1.27-alpine AS runtime
COPY nginx.conf /etc/nginx/conf.d/default.conf
COPY --from=build /app/dist /usr/share/nginx/html
EXPOSE 8080
```

`nginx.conf` (listen on 8080, SPA fallback):
```nginx
server {
  listen 8080;
  root /usr/share/nginx/html;
  index index.html;
  location / { try_files $uri $uri/ /index.html; }
}
```

**Important:** because `VITE_API_BASE_URL` is baked at build time, the backend
FQDN must be known before building the frontend image. Deployment order in §5.7
reflects this (deploy backend first, then build/deploy frontend with its FQDN).
The CI/CD pipeline (§11) MUST honor this same ordering.

## 5. Azure architecture

### 5.1 Topology summary

```
                    Internet
                       │
          ┌────────────┴─────────────┐
          │                          │
   [Frontend Container App]   [Backend Container App]
   todo-web (nginx SPA)       todo-api (.NET 10)
   external ingress :8080     external ingress :8080
          │                          │
          └── browser calls ────────►│  (CORS-allowed)
                                      │
                                      ▼
                        [Azure DB for PostgreSQL
                         Flexible Server]  todo-pg
                         (public access + firewall,
                          TLS required)
```

Both apps run in the **same Container Apps Environment**. Images come from a
shared **Azure Container Registry**. The database is a **PostgreSQL Flexible
Server**.

### 5.2 Why Azure Container Apps for both (deployment-target justification)

The requirement gives a choice between "both in Container Apps" vs "frontend
static hosting + backend container app". **Decision: both run as Container Apps.**

Rationale:
- **Consistency & simplicity for a reference app**: one deployment mechanism,
  one registry, one environment, one set of `az containerapp` commands. The
  engineer and tester deal with a single pattern rather than two (ACA + Static
  Web Apps have different CLIs, auth, and config models).
- Azure Static Web Apps would be cheaper/simpler *for the frontend alone*, but
  it introduces a second service, a different deploy flow, and its own
  API-linking model. For a demo whose whole point is "containers on ACA," the
  uniformity is worth more than the marginal cost saving.
- Both containers are trivially small; ACA scale-to-zero (see §5.6) keeps idle
  cost near zero, so hosting the SPA in a container is not meaningfully more
  expensive here.

This choice is a documented assumption (§9); if cost minimization later becomes
a priority, moving the frontend to Static Web Apps is a clean swap.

Suggested names (engineer should templatize a `RESOURCE_GROUP` and `LOCATION`;
defaults below). Region default: **eastus** (broad availability of ACA +

|------------------------------|----------------------------------------|-----------------------------|

### 5.4 Networking / connectivity

Keep it simple with **public access + firewall + TLS** (no VNet injection):

- PostgreSQL Flexible Server is created with **public network access**.
- Firewall rule: enable **"Allow public access from any Azure service within
  Azure"** (`0.0.0.0` special rule) so the Container Apps egress reaches
  Postgres without pinning ephemeral outbound IPs. This is acceptable for a
  demo and documented as such.
- **TLS is required** on the connection (`Ssl Mode=Require` in the Npgsql
  connection string). Do not disable SSL.
- Both Container Apps use **external ingress** (public FQDN). Backend ingress is
  public so the browser SPA can call it directly (CORS restricts origins).

Documented trade-off: for production you would use VNet-integrated Container
Apps + Postgres with a private endpoint / delegated subnet and no public
access. That is intentionally out of scope (§8).

### 5.5 Secrets / config management

- **Container Apps secrets** (not Key Vault) hold the Postgres connection
  string. Rationale: one fewer resource, no Key Vault access-policy/RBAC setup,
  adequate for a demo. Key Vault is noted as the production upgrade path.
- Backend `todo-api` gets a secret named `todo-db-connection` whose value is the
  full Npgsql connection string, surfaced to the app as env var
  `ConnectionStrings__TodoDb`.
- ACR pull: use a **managed identity** on the Container Apps (assign `AcrPull`)
  if straightforward; otherwise fall back to admin-user registry credentials
  stored as a Container Apps secret. Engineer picks whichever the tooling makes
  simplest and records the choice in `changes.md`.
- Postgres admin username/password are set at server creation and referenced
  only inside the connection string secret. Do not commit them; pass via
  environment/CLI variables at deploy time.

Example connection string (values are placeholders):
```
Host=pg-todo-demo.postgres.database.azure.com;Port=5432;Database=tododb;Username=todoadmin;Password=<PWD>;Ssl Mode=Require;Trust Server Certificate=true
```

### 5.6 Scaling

- Backend `todo-api`: min replicas **0**, max **3**, scale on HTTP concurrency
  (default rule, ~50 concurrent requests). Scale-to-zero is fine for a demo
  (accept cold-start latency).
- Frontend `todo-web`: min replicas **1** (so the SPA loads instantly), max
  **2**. Optionally 0 if cost is paramount — default to 1 for better demo UX.
- CPU/memory per replica: **0.25 vCPU / 0.5 GiB** (smallest sensible size) for
  both apps.

### 5.7 Deployment topology & ordering

Because the frontend bakes the backend URL at build time (§4.4), order matters:

1. Create RG, ACR, Log Analytics, Container Apps environment.
2. Create Postgres Flexible Server + `tododb` database + firewall rule.
3. Build & push **backend** image to ACR; create `todo-api` Container App with
   the DB connection secret and external ingress on port 8080. Capture its FQDN.
4. Build **frontend** image with `--build-arg VITE_API_BASE_URL=https://<todo-api FQDN>`;
   push; create `todo-web` Container App (external ingress, port 8080). Capture
   its FQDN.
5. Update backend `Cors:AllowedOrigins` (env var `Cors__AllowedOrigins__0`) to
   the `todo-web` FQDN and revision-restart `todo-api`.

The engineer must write these as concrete, runnable `az` commands in
`changes.md` (parameterized by RG/location/names). For the manual bootstrap path
these remain reference commands; the **repeatable** path is now the Bicep + CI/CD
in §11. **Do not auto-provision** — the architect and engineer only document
commands; a human (or the CD pipeline, once its identity is set up) runs them.

Reference command sketch (illustrative — engineer/devops to finalize; the Bicep
in §11 supersedes this for repeatable deploys):
```bash
az group create -n rg-todo-demo -l eastus
az acr create -g rg-todo-demo -n <acrname> --sku Basic
az containerapp env create -g rg-todo-demo -n cae-todo-demo -l eastus
az postgres flexible-server create -g rg-todo-demo -n pg-todo-demo \
  --admin-user todoadmin --admin-password <PWD> --tier Burstable --sku-name Standard_B1ms \
  --version 16 --database-name tododb --public-access 0.0.0.0
az acr build -r <acrname> -t todo-api:latest ./backend            # uses backend Dockerfile
az containerapp create -g rg-todo-demo -n todo-api --environment cae-todo-demo \
  --image <acrname>.azurecr.io/todo-api:latest --target-port 8080 --ingress external \
  --secrets todo-db-connection="<connstr>" \
  --env-vars ConnectionStrings__TodoDb=secretref:todo-db-connection
# then frontend build with the todo-api FQDN, then create todo-web similarly
```

## 7. Non-functional considerations (kept minimal)

- **Auth**: none. Single anonymous user. Explicitly out of scope.
- **Security basics that ARE in scope**: TLS to Postgres; secrets not committed
  to source; CORS restricted to the known frontend origin(s); parameterized
  queries via EF Core (no raw SQL).
- **Logging**: default ASP.NET Core console logging → captured by Container Apps
  / Log Analytics. No custom telemetry/APM.
- **Health**: `/health` endpoint wired to Container Apps probes.
- **Error handling**: return proper status codes + `ProblemDetails`; the SPA
  shows a simple inline error message on failure.
- **Cost**: Burstable Postgres (`Standard_B1ms`), Basic ACR, ACA scale-to-zero
  on backend. Intended to sit in the low single-digit dollars/month when idle.
- **Testing expectation** (for the tester agent): backend integration tests
  against the API covering each endpoint + validation + 404 paths (in-memory or
  Testcontainers Postgres — tester's choice). Frontend tests are optional/light
  (a smoke test of `useTodos`/rendering is sufficient). Do not over-invest.

## 8. Explicitly out of scope

- Authentication, authorization, user accounts, multi-tenancy.
- Pagination, sorting options, search/filtering beyond the fixed
  newest-first list.
- Soft deletes, audit history, todo categories/tags, due dates, reminders.
- VNet-integrated / private-endpoint networking; the demo uses public access +
  firewall + TLS.
- Azure Key Vault (Container Apps secrets are used instead).
- Static Web Apps hosting for the frontend (frontend is containerized on ACA).
- Rate limiting, WAF, custom domains, CDN.
- **Multi-environment promotion** (dev/staging/prod). CI/CD (§11) targets a
  **single environment** deployed from `main`. Adding staging is a future cycle.
- **Automated creation of cloud identities / credentials / RBAC.** The CI/CD
  OIDC identity and role assignments are a **manual one-time human step**
  (§11.6); agents never create them.
- **Database migration as a separate pipeline stage.** Migrations still run at
  app startup (§3.4); CD does not run `dotnet ef database update` as its own
  job.

## 11. CI/CD & Infrastructure-as-Code (extension — this cycle's scope)

This section defines the delivery layer for the app. It is authored by the
architect for a downstream **`devops` subagent** to implement. The devops agent
operates in **PROPOSE mode** (§11.8): it *authors* IaC and pipeline YAML and
*documents* commands, but never provisions, deploys, or creates
credentials/identities itself.

### 11.1 Goals & non-goals

**Goals**
- Reproducible, reviewable infrastructure via IaC (no more click-ops / ad-hoc
  `az create` as the source of truth).
- PR-gated delivery: every change is validated by CI before it can merge.
- Automated deploy to Azure Container Apps on merge to `main`.
- Secretless CI→Azure authentication (OIDC / workload identity federation).
- Cheap by default — demo-grade SKUs everywhere (§11.9).

**Non-goals** (see also §8)
- Multi-environment promotion (single environment from `main`).
- Blue/green or canary rollouts (single-revision replace is fine).
- Automated identity/RBAC/GitHub-secret creation (manual bootstrap, §11.6).
- A dedicated DB-migration pipeline stage (migrations run at app startup).

### 11.2 IaC tool decision — **Bicep** (with rationale)

**Decision: use Bicep**, not Terraform.

Rationale:
- **No state backend to manage.** Terraform would require provisioning and
  securing a remote state backend (storage account + blob container + state
  locking) before it can run in CI — extra resources and a chicken-and-egg
  bootstrap. Bicep uses Azure Resource Manager's server-side deployment state,
  so there is nothing extra to stand up.
- **Azure-native, first-class ACA + Postgres Flexible Server support**, and it
  ships with the `az` CLI already present in this environment (verified: az
  2.63.0). No provider/plugin download step.
- **Lowest ceremony for a single-cloud, single-subscription demo.** The whole
  point of this app is Azure containers; Bicep keeps the toolchain to one thing.

Terraform is the documented alternative and would be preferred if the project
ever went multi-cloud, wanted an explicit `plan` artifact for review, or needed
Terraform-specific module ecosystems. If a reviewer insists on Terraform, the
module boundaries in §11.3 map 1:1 to Terraform resources; only the state-backend
bootstrap and the `what-if`→`plan` step change.

### 11.3 What the devops agent must produce — Bicep IaC

Directory: **`infra/`** at the repo root.

```
infra/
  main.bicep                 # subscription- or RG-scoped entry point
  main.parameters.json       # default (non-secret) parameter values
  modules/
    registry.bicep           # ACR (Basic)
    loganalytics.bicep       # Log Analytics workspace
    acaEnvironment.bicep     # Container Apps managed environment
    postgres.bicep           # Postgres Flexible Server + tododb + firewall rule
    containerApp.bicep       # reusable module for one Container App (params: name,
                             #   image, targetPort, external ingress, env vars,
                             #   secrets, min/max replicas, cpu/memory)
  README.md                  # how to deploy manually + how CD consumes it
```

Requirements the Bicep must satisfy:
- **Scope:** `main.bicep` targets `resourceGroup` scope; the resource group
  itself is created out-of-band (documented `az group create` in §11.6) OR
  `main.bicep` is `subscription`-scoped and creates the RG. Devops agent picks
  one and documents it; **RG name `rg-todo-demo`, region `eastus`** are the
  defaults and must match §5.3.
- **Parameters** (all with demo-safe defaults): `location`, `resourcePrefix`/
  names, `acrName` (with uniqueness suffix via `uniqueString(resourceGroup().id)`),
  `postgresAdminUser`, image tags for `todo-api` and `todo-web`, and the
  frontend/backend replica + resource sizing from §5.6.
- **Secrets are NOT hard-coded in Bicep or parameter files.** The Postgres admin
  password and the assembled connection string are passed as **secure
  parameters** (`@secure()`), supplied at deploy time from a GitHub Actions
  secret / pipeline secret (§11.6). Parameter files in git contain only
  non-secret values.
- **Resources produced** (matches §5.3): ACR (Basic), Log Analytics, ACA
  environment, Postgres Flexible Server + `tododb` + the `0.0.0.0` "allow Azure
  services" firewall rule, and the two Container Apps (`todo-api`, `todo-web`).
- **Identity / ACR pull:** enable a **system-assigned managed identity** on each
  Container App and grant it `AcrPull` on the registry (role assignment in
  Bicep). This is the preferred ACR-pull mechanism from §5.5; the admin-user
  fallback should not be used in the IaC path.
- **Backend Container App** gets the DB connection string as a Container Apps
  **secret** `todo-db-connection`, surfaced as env `ConnectionStrings__TodoDb`,
  plus `Cors__AllowedOrigins__0` set to the frontend FQDN. Because the frontend
  FQDN and the frontend image both depend on ordering (§4.4/§5.7), see §11.7 for
  how the pipeline sequences this within a single Bicep deployment vs. a two-step
  deploy.
- **Outputs:** `acrLoginServer`, `todoApiFqdn`, `todoWebFqdn`, ACA env id —
  consumed by the CD pipeline and printed for humans.
- Must pass `az bicep build` and `az bicep lint` with no errors (CI enforces
  this, §11.4).

### 11.4 GitHub Actions — CI workflow (`.github/workflows/ci.yml`)

**Trigger:** `pull_request` targeting `main` (and `workflow_dispatch` for manual
runs). This is the **required status check** for the branch protection in §11.7.

**Jobs (build/validate only — NO push, NO deploy, NO Azure login required):**
1. **backend** — set up .NET 10, `dotnet restore`, `dotnet build -c Release`,
   `dotnet test` (runs the tester agent's xUnit suite). Fail on any test failure.
2. **frontend** — set up Node 22, `npm ci`, `npm run build`, and lint/typecheck
   if configured. (`VITE_API_BASE_URL` can be a placeholder for the build-check.)
3. **docker** — `docker build` both images (backend context `backend/`, frontend
   context `frontend/` with a dummy `--build-arg VITE_API_BASE_URL`) to prove the
   Dockerfiles build. Do **not** push.
4. **iac** — `az bicep build infra/main.bicep` + `az bicep lint`. Optionally a
   `what-if` against the target RG **only if** OIDC is wired for PRs; default is
   lint-only so CI needs no cloud credentials and is safe on fork PRs.

CI must be fast and credential-free by default so it can run on any PR safely.

### 11.5 GitHub Actions — CD workflow (`.github/workflows/cd.yml`)

**Trigger:** `push` to `main` (i.e., on merge) + `workflow_dispatch`.
**Concurrency:** a single `cd-main` concurrency group so overlapping merges
don't race a deploy.
**Permissions:** `id-token: write` (OIDC) + `contents: read`.

**Steps (in order — honors the §4.4/§5.7 backend-before-frontend constraint):**
1. `azure/login@v2` using OIDC (`client-id`, `tenant-id`, `subscription-id` from
   GitHub **variables/secrets** — see §11.6). No client secret.
2. **Provision/update infra:** `az deployment group create` (or `sub` scope)
   with `infra/main.bicep`, passing the secure Postgres password + assembled
   connection string from GitHub secrets. This is idempotent — safe to run every
   deploy. Capture outputs (`acrLoginServer`, `todoApiFqdn`).
3. **Build & push backend image** to ACR (`az acr build -r <acr> -t todo-api:${{ github.sha }} ./backend`,
   or docker build + `az acr login` + push). Tag with the commit SHA (and
   optionally `latest`).
4. **Update backend Container App** to the new image
   (`az containerapp update ... --image <acr>/todo-api:<sha>`); read back its
   FQDN.
5. **Build & push frontend image** with `--build-arg VITE_API_BASE_URL=https://<todoApiFqdn>`.
6. **Update frontend Container App** to the new image; read back its FQDN.
7. **Reconcile CORS:** ensure backend `Cors__AllowedOrigins__0` = frontend FQDN
   (set via the Bicep deploy in step 2 on subsequent runs, or an
   `az containerapp update` here on first deploy). Document which approach is
   used.
8. Print final FQDNs in the job summary.

Note the ordering rationale: the frontend image must bake the backend FQDN, and
the backend must allow the frontend origin via CORS — a two-phase apply. The
devops agent may either (a) run Bicep once for infra then imperatively update
images (recommended — simplest), or (b) parameterize images into Bicep and run
it twice. Document the chosen approach in `infra/README.md` and `changes.md`.

### 11.6 Identity & credential strategy — **OIDC federated credentials**

**Decision: GitHub Actions authenticates to Azure via OpenID Connect (workload
identity federation), NOT a service-principal client secret.**

Rationale: no long-lived secret stored in GitHub to leak or rotate; Azure mints
a short-lived token scoped to a specific repo/branch/environment per run. This is
the current Microsoft-recommended pattern for GitHub→Azure.

**What the pipelines reference (never create):**
- GitHub repository (or environment) **variables**: `AZURE_CLIENT_ID`,
  `AZURE_TENANT_ID`, `AZURE_SUBSCRIPTION_ID`.
- GitHub **secrets**: `PGADMIN_PASSWORD` (Postgres admin password) and, if the
  connection string is assembled outside Bicep, `TODO_DB_CONNECTION`. These feed
  the `@secure()` Bicep params (§11.3).

**One-time human bootstrap (MANUAL — never run by any agent).** The devops agent
must WRITE these exact commands into `infra/README.md` / `changes.md` for a human
to execute, and must explicitly label them "manual, run once, by a human":

```bash
# 1. Create an Entra app registration (or user-assigned managed identity) for CI.
az ad app create --display-name "gh-todo-demo-cicd"
#    → capture appId (this becomes AZURE_CLIENT_ID) and create a service principal:
az ad sp create --id <appId>

# 2. Add a federated credential binding the app to this repo's main branch
#    (repeat with subject for pull_request / environment as needed).
az ad app federated-credential create --id <appId> --parameters '{
  "name": "gh-todo-demo-main",
  "issuer": "https://token.actions.githubusercontent.com",
  "subject": "repo:<org>/<repo>:ref:refs/heads/main",
  "audiences": ["api://AzureADTokenExchange"]
}'

# 3. Grant the SP least-privilege RBAC on the target resource group.
az role assignment create --assignee <appId> --role Contributor \
  --scope /subscriptions/<subId>/resourceGroups/rg-todo-demo
az role assignment create --assignee <appId> --role AcrPush \
  --scope /subscriptions/<subId>/resourceGroups/rg-todo-demo/providers/Microsoft.ContainerRegistry/registries/<acrName>

# 4. Set the GitHub variables/secrets (human, via gh CLI or the UI).
gh variable set AZURE_CLIENT_ID --body <appId>
gh variable set AZURE_TENANT_ID --body <tenantId>
gh variable set AZURE_SUBSCRIPTION_ID --body <subId>
gh secret set PGADMIN_PASSWORD    # prompts for value
```

Notes:
- RBAC is scoped to the **resource group**, not the whole subscription
  (least privilege). `Contributor` on the RG is the pragmatic demo choice; a
  reviewer may tighten to specific resource-type roles.
- If the RG is created by a `subscription`-scoped Bicep deploy, the SP also needs
  `Contributor` at subscription scope OR the RG must be pre-created by the human
  (recommended: pre-create the RG, keep the SP scoped to the RG).
- **The agents must not run any command in this subsection.** They only author
  and document it.

### 11.7 Branch / PR workflow & branch protection

- **Trunk = `main`.** It is the only deployable branch; CD (§11.5) triggers on
  push to `main`.
- **Feature work happens on branches off `main`**, named `pipeline/*` (this
  cycle: `pipeline/todo-app-azure-cicd`) or `feature/*`.
- **No direct pushes to `main`.** All changes land via **Pull Request**.
- **Branch protection rules on `main`** (documented for a human/`gh` to apply —
  configuring branch protection is a repo-admin action, not something agents
  provision):
  - Require a pull request before merging.
  - Require the **CI workflow (§11.4) to pass** as a required status check.
  - Require the branch to be up to date before merging.
  - Dismiss stale approvals / require at least one review (the pipeline's own
    review gate counts).
  - Disallow force-pushes and deletion of `main`.
  - **Squash merge** preferred (linear history).
- **Single environment:** merges to `main` deploy straight to the one demo
  environment. There is no staging/prod split this cycle (§8, §11.1). Adding a
  GitHub `production` Environment with required reviewers is the natural next
  step and is called out as a future enhancement.

### 11.8 PROPOSE mode — what the devops agent may and may not do

The `devops` subagent runs in **PROPOSE mode**:

- **MAY:** author files under `infra/`, `.github/workflows/`, and
  `azure-pipelines.yml`; run read-only `az`/`bicep` validation
  (`az bicep build/lint`, `az ... show/list`, `az deployment ... what-if`);
  document exact commands for humans.
- **MUST NOT:** run any `az ... create/update/delete`, `az deployment ... create`,
  `az containerapp update`, `az acr build/push`, or any provisioning; create or
  modify Entra app registrations, federated credentials, RBAC role assignments,
  or GitHub secrets/variables; push to `main`; alter this spec, CLAUDE.md, or

- Deployment happens only when a **human** (or the CD pipeline, once a human has
  completed the §11.6 bootstrap) runs it. The pipelines the agent writes are the
  automation; the agent itself never fires them.

### 11.9 Cost-consciousness guidance for PROPOSE mode (SKU guardrails)

This is a **demo**. The devops agent's proposed IaC/pipelines MUST default to the
cheapest reasonable SKUs. Concretely:

- **Azure Container Apps:** **Consumption** workload profile (the default
  Consumption plan — pay-per-use, scale-to-zero). Do NOT propose a Dedicated
  workload profile. Backend min replicas **0**; frontend min **1** (per §5.6).
  0.25 vCPU / 0.5 GiB per replica.
- **PostgreSQL Flexible Server:** **Burstable** tier, **`Standard_B1ms`**, smallest
  storage (32 GiB), **no** high-availability, **no** read replicas, geo-redundant
  backup **disabled** (locally-redundant, minimal retention). PostgreSQL 16.
- **Azure Container Registry:** **Basic** SKU. No geo-replication, no Premium
  features.
- **Log Analytics:** pay-as-you-go, **30-day retention** (do not raise it),
  daily cap optional. Reuse the single workspace for the ACA environment.
- **No extra cost centers:** no NAT Gateway, no VNet/private endpoints, no
  Application Gateway/WAF, no Front Door/CDN, no Key Vault, no Bastion — all
  explicitly out of scope (§8) and each avoids monthly cost.
- **Single region, single environment, single of everything** (one ACR, one ACA
  env, one Postgres server).
- If the devops agent believes a costlier SKU is genuinely required, it must NOT
  silently choose it — it must call it out as an explicit note in `changes.md`
  with the cost rationale for reviewer sign-off.

Target: idle cost in the low single-digit USD/month, dominated by the Burstable
Postgres server (the only always-on component).

A functional parity pipeline for teams on Azure DevOps, at the repo root:

- **`main` trigger** → the same CD steps as §11.5.

## 12. Observability / Distributed Tracing (extension — this cycle's scope)

Added 2026-07-27 on branch `pipeline/appinsights-tracing` (off `main`), review
cycle 1 of up to 3. This section is **additive**: it does not change §1–§11.
It introduces end-to-end distributed tracing for the **.NET 10 backend**,
correlated by a `traceId` and exported to **Azure Application Insights**.

### 12.1 Requirement (verbatim)

> "The application should be able to trace an entire request response. The .net
> application should be able to log in AppInsights using traceId."

### 12.2 Goal

- Every inbound HTTP request to `todo-api` produces a **single, correlated
  distributed trace** covering the full request/response lifecycle: the ASP.NET
  Core request (server span), any outbound `HttpClient` calls, and the
  **EF Core / Npgsql database calls** made while handling that request — all
  under one W3C `traceId`.
- All application log lines (`ILogger`) emitted while handling a request are
  **stamped with that same `TraceId` (and `SpanId`)**, so logs in Application
  Insights (and in the console / Log Analytics) can be pivoted by `traceId` to
  reconstruct exactly what happened for one request.
- The trace + correlated logs are queryable in Application Insights
  (`requests`, `dependencies`, `traces` tables; end-to-end transaction view).

### 12.3 Technical approach — `Azure.Monitor.OpenTelemetry.AspNetCore`

**Decision: use the `Azure.Monitor.OpenTelemetry.AspNetCore` NuGet package** —
Microsoft's current (2024+) recommended "one-liner" Application Insights
integration for ASP.NET Core, built on **OpenTelemetry** and emitting **W3C
Trace Context** by default. This supersedes the legacy
`Microsoft.ApplicationInsights.AspNetCore` classic SDK, which must **not** be
used here.

Rationale:
- It bundles and auto-configures the OpenTelemetry tracing, metrics, and logging
  providers and points them at Application Insights via a single call. Out of the
  box it instruments **ASP.NET Core incoming requests**, **`HttpClient` outgoing
  calls**, and (with the Npgsql/EF Core instrumentation it enables) **database
  calls**, producing one correlated trace — exactly the "trace an entire
  request/response" requirement.
- It is the forward-looking, vendor-neutral path (OpenTelemetry) while still
  being first-party Microsoft-supported for App Insights.
- Correlation uses W3C `traceparent`, so traces propagate correctly across the
  SPA-to-API boundary if/when the frontend ever participates (see §12.7).

**Wiring (engineer guidance — do not implement in this cycle, spec only).**
In `Program.cs`, after `var builder = WebApplication.CreateBuilder(args);` and
alongside the existing service registrations (Program.cs currently registers
controllers, Swagger, `DbContext`, CORS — none of which change):

```csharp
// Add Azure Monitor (Application Insights) via OpenTelemetry.
// Reads APPLICATIONINSIGHTS_CONNECTION_STRING from configuration/env automatically.
builder.Services.AddOpenTelemetry().UseAzureMonitor();

// Ensure EF Core / Npgsql database calls are captured as trace dependencies.
builder.Services.ConfigureOpenTelemetryTracerProvider(tracing =>
    tracing.AddNpgsql());   // from Npgsql.OpenTelemetry
```

Package additions to `backend/src/TodoApi/TodoApi.csproj`:
- `Azure.Monitor.OpenTelemetry.AspNetCore` (latest stable compatible with
  `net10.0`; engineer pins the exact version and records it in `changes.md`).
- `Npgsql.OpenTelemetry` (Npgsql's OpenTelemetry integration, so Postgres
  queries appear as `dependencies` spans within the trace). If the installed
  Npgsql version emits its `ActivitySource` without this helper, the engineer
  documents the actual mechanism used; the requirement is simply that DB calls
  show up as child spans of the request.

If the exact package versions for `net10.0` are unavailable at build time, the
engineer uses the nearest compatible stable release and notes the substitution
in `changes.md` (consistent with §9.5).

### 12.4 Relationship to existing logging — COEXIST, do not replace

The current app (`Program.cs`) uses **default ASP.NET Core `ILogger` / console
logging** only, with **no telemetry** (confirmed: no OpenTelemetry or App
Insights packages in `TodoApi.csproj` today; §7 "Logging" describes exactly
this). This tracing feature **augments** that setup; it does **not** rip it out:

- **Console logging stays.** `UseAzureMonitor()` **adds** an OpenTelemetry
  logging provider to the existing logging pipeline; it does not remove the
  console provider. Container Apps to Log Analytics console capture (§7) keeps
  working unchanged, so nothing is lost if App Insights is misconfigured.
- **`traceId` on every log line is automatic — no manual enrichment needed.**
  ASP.NET Core sets `Activity.Current` per request (the ambient `Activity`
  carries the W3C `TraceId`/`SpanId`). `Microsoft.Extensions.Logging` already
  attaches the current `Activity`'s `TraceId` and `SpanId` to every `ILogger`
  record. Once the OpenTelemetry/Azure Monitor logging provider is registered,
  those log records are exported to App Insights `traces` **already correlated**
  to the request's `traceId`. Existing `logger.LogInformation(...)` /
  `logger.LogError(...)` calls (e.g. the migration logs in `Program.cs`) require
  **no code change** to become trace-correlated.
- **No structured-logging library swap.** We do **not** introduce Serilog or a
  custom enricher — the built-in `Activity`-to-`ILogger` scope correlation is
  sufficient for the requirement. Keeping the default logging stack is
  consistent with the project's "keep it simple" principle (§1).
- **Confirmed behavior to document for the engineer:** the correlation works
  because of `Activity.Current`; the engineer should **not** disable activity
  tracking and should leave the default `TraceId`/`SpanId` activity tracking
  enabled.

### 12.5 Configuration — connection string via env var / Container Apps secret

- The Application Insights **connection string** is read from the standard env
  var **`APPLICATIONINSIGHTS_CONNECTION_STRING`**, which
  `Azure.Monitor.OpenTelemetry.AspNetCore` reads **automatically** (no code
  needs to reference it). It is **never hardcoded** and never committed.
- This mirrors exactly how the Postgres connection string is handled today
  (§3.3 / §5.5): a **Container Apps secret** whose value is injected as an
  environment variable on the `todo-api` Container App.
  - Secret name (suggested): **`appinsights-connection`**.
  - Env var surfaced to the app: **`APPLICATIONINSIGHTS_CONNECTION_STRING`**
    (`secretref:appinsights-connection`).
  - Note: unlike the Postgres var, this env var name has **no** `__` section
    syntax — it is a flat SDK-recognized name, so use it verbatim.
- **Local development:** the connection string is simply left **unset** locally.
  When `APPLICATIONINSIGHTS_CONNECTION_STRING` is absent the exporter has no
  endpoint and quietly does not export to Azure — the app still runs and console
  logs still work. Tracing itself (the `Activity`/`traceId` flow) is still
  active in-process, which is what the tests in §12.8 assert. Do **not** put a
  real connection string in `appsettings*.json`.
- Config precedence is the standard .NET one (env var overrides `appsettings`);
  the value only ever comes from the environment in Azure.

### 12.6 Azure architecture — one workspace-based Application Insights resource

**One new Azure resource is required: an Application Insights component,
workspace-based, backed by the EXISTING Log Analytics workspace
`log-todo-demo`.** Do **not** create a second Log Analytics workspace.

- **Type:** `Microsoft.Insights/components`, `kind: web`, `Application_Type:
  web`, with `WorkspaceResourceId` pointing at the existing `log-todo-demo`
  workspace (provisioned per §5.3 / §11.9 as the ACA environment's workspace).
  Classic (non-workspace) Application Insights is retired and must not be used.
- **Suggested name:** `appi-todo-demo` (follows the `<type-abbrev>-todo-demo`
  convention from architecture-memory; `appi-` is the standard abbreviation for
  Application Insights).
- **Why reuse `log-todo-demo`:** workspace-based App Insights stores its data in
  a Log Analytics workspace. Reusing the single existing workspace keeps the
  "single of everything" posture (§11.9), keeps all telemetry queryable in one
  place, and avoids a second cost center / second retention setting.
- **Region:** same region as the workspace / ACA environment. App Insights
  follows the **workspace's** region — this is independent of any Postgres
  region-restriction decision recorded in architecture-memory. The devops agent
  must place `appi-todo-demo` in the same region as `log-todo-demo`.

## 13. Identity & Secrets Policy — managed-identity-first (extension — this cycle's scope)

Added 2026-07-27 on branch `pipeline/appinsights-tracing`, same cycle as §12.
This section encodes a **project-wide policy** from the human and applies it
critically to every trust boundary in the app. It **supersedes** the "Container
Apps secrets, not Key Vault" default stated in **§5.5**, and **revises the
connection-string-as-secret approach in §12.5** (see §13.4). §5.5 and §12.5
remain in the document for history; where they conflict with this section, **this
section wins.**

### 13.1 The policy (verbatim)

> "Applications that can use identity manager [managed identity] to authenticate
> should use it. If applications can not use it, then it should use KeyVault to
> store secrets or connection strings."

### 13.2 Interpretation & decision hierarchy

For **every** credential/secret an application component needs, apply this order:

1. **Managed identity (Entra) auth — REQUIRED if the target service supports it.**
   No secret is stored at all; the Container App's system-assigned managed
   identity (already enabled per §11.3) authenticates directly.
2. **Azure Key Vault — only if (1) is genuinely impossible** for that target.
   The secret lives in Key Vault; the Container App's managed identity is granted
   `Key Vault Secrets User` (RBAC, not legacy access policies) and the value is
   surfaced via a **Container Apps Key Vault reference** (see §13.6).
3. **Container Apps secret (raw value) — deprecated / last resort only**, allowed
   solely for values that are neither an Azure-service credential nor storable in
   Key Vault (none remain after this cycle — see §13.3).

Applying this hierarchy to the app **eliminates every runtime application secret**
(§13.3–§13.5). As a result **no Key Vault resource is provisioned this cycle** —
the "cannot use managed identity" branch of the policy is not triggered by any
current secret. The Key Vault pattern is still specified (§13.6) as the standing
rule for any *future* secret that cannot use managed identity, so future cycles
don't re-derive it.

### 13.3 Per-secret classification (the authoritative table)

| # | Trust boundary | Secret today | Policy outcome | Mechanism |
|---|----------------|--------------|----------------|-----------|
| 1 | `todo-api` → PostgreSQL Flexible Server | Password in `todo-db-connection` Container Apps secret (§5.5) | **Managed identity (Entra) — password secret DROPPED** | §13.4 |
| 2 | `todo-api` → Application Insights | AI connection string as Container Apps secret (§12.5) | **Managed identity (Entra) for auth; connection string demoted to non-secret env var** | §13.5 |
| 3 | `todo-api`/`todo-web` → ACR (image pull) | none (AcrPull via MI) | **Already compliant** — no change | §13.7 |
| 4 | GitHub Actions / Azure DevOps → Azure subscription | none (OIDC federation) | **Compliant in spirit** (external workload → federated identity, the MI-equivalent) | §13.8 |
| 5 | Postgres **admin** login (deploy-time only) | `PGADMIN_PASSWORD` GitHub secret / `@secure()` Bicep param (§11.6) | **Out of app-secret scope** — CI/CD deploy-time secret, not an application runtime secret; not used by the running app | §13.9 |

**Result: zero application runtime secrets remain.** No component falls to the
Key Vault branch. `todo-web` (nginx SPA) holds no credentials at all.

### 13.4 Postgres — switch to managed-identity (Entra) auth [supersedes §5.5 for #1]

**Decision: `todo-api` authenticates to PostgreSQL Flexible Server using its
system-assigned managed identity via Microsoft Entra authentication. The
password and the `todo-db-connection` secret are removed from the Azure
deployment.** Verified viable with Npgsql on .NET 10 (see Sources at end).

How it works (engineer guidance — spec only, no code this cycle):
- Add the **`Azure.Identity`** package to `TodoApi.csproj`.
- Build the `DbContext` over an **`NpgsqlDataSource`** whose password is supplied
  by a **token provider** rather than a static string. Use Npgsql's
  **periodic password provider** so the ~60-minute Entra access token is
  refreshed automatically (do not fetch once at startup):

  ```csharp
  // Azure only. Acquire an Entra token for the Postgres resource via the app's
  // managed identity and hand it to Npgsql as the (rotating) password.
  var credential = new DefaultAzureCredential();               // ManagedIdentityCredential in ACA
  var dataSourceBuilder = new NpgsqlDataSourceBuilder(baseConnString); // no Password= in this string
  dataSourceBuilder.UsePeriodicPasswordProvider(async (_, ct) =>
  {
      var token = await credential.GetTokenAsync(
          new TokenRequestContext(new[] { "https://ossrdbms-aad.database.windows.net/.default" }), ct);
      return token.Token;
  }, TimeSpan.FromMinutes(50), TimeSpan.FromSeconds(5));
  builder.Services.AddDbContext<TodoDbContext>(o => o.UseNpgsql(dataSourceBuilder.Build()));
  ```

- **Connection string in Azure becomes passwordless and non-secret**:
  `Host=<server>.postgres.database.azure.com;Port=5432;Database=tododb;Username=<managed-identity-name>;Ssl Mode=Require;Trust Server Certificate=true`.
  - `Username` = the **managed identity's name** (the Postgres role created in the
    bootstrap below), NOT `todoadmin`.
  - This string contains no credential, so it is delivered as a **plain env var**
    `ConnectionStrings__TodoDb` (no Container Apps secret, no Key Vault).
- **Token scope:** `https://ossrdbms-aad.database.windows.net/.default`. **SSL is
  still required** (unchanged from §5.4).

**Local development is unchanged and stays on password auth** against the local
Docker Postgres (§6.2/§6.3) — that container is not Entra-enabled and the local
password is not an Azure secret, so it is out of policy scope. The engineer must
**gate the token-provider wiring** so it is used **only in Azure**, e.g. a config
flag `Postgres__UseEntraAuth=true` (set on the `todo-api` Container App; unset
locally). When the flag is off, keep today's `UseNpgsql(connectionString)` path
with the local password. `dotnet ef` design-time and startup `Migrate()` continue
to work: locally against local Postgres; in Azure the startup `Migrate()` runs
under the managed identity's Entra token (the identity's Postgres role must own /
be able to create the schema — granted in the bootstrap).

**New one-time MANUAL bootstrap (human-run, never by an agent — extends §11.6).**
Managed-identity Postgres auth requires steps that cannot live in Bicep because
they run *inside* the database as the Entra admin:
1. Enable **Microsoft Entra authentication** on the Flexible Server and set an
   **Entra administrator** (a human/group). Bicep *can* set the server's Entra
   admin via the `administrators` child resource and enable Entra auth; the
   devops agent should do that part in IaC.
2. Connect to the **`postgres`** database as that Entra admin and create a role
   for the app's managed identity:
   ```sql
   -- run as the Entra admin, connected to the `postgres` database
   select * from pgaadauth_create_principal('<todo-api-managed-identity-name>', false, false);
   -- then grant it rights on tododb (connect, and schema ownership/DDL for startup Migrate())
   ```
   This SQL step is **manual** (like the §11.6 OIDC bootstrap) and must be
   documented verbatim by devops in `infra/README.md`, labeled "manual, run once,
   by a human."
- Optional hardening (note, not required this cycle): set the server to
  **Entra-authentication-only** to eliminate the admin password entirely; kept
  as dual-auth for demo simplicity so the admin login still works for break-glass.

**Trade-off assessment (why we adopt it despite added complexity):** this adds a
token-provider data source, a config gate for local vs. Azure, and a manual
in-database principal step. That is moderate, well-trodden complexity and it is
exactly what the policy mandates ("applications that *can* use managed identity
*should*"). Postgres *can*, so we adopt it and remove a stored password. No
blocker was found that would justify keeping the password.

### 13.5 Application Insights — Entra auth, connection string demoted [revises §12.5]

**Decision: `todo-api` authenticates telemetry ingestion with its managed
identity (Entra), and the Application Insights connection string is demoted from
a Container Apps *secret* to a plain non-secret env var.** Verified: Azure Monitor
Distro supports Entra auth via `AzureMonitorOptions.Credential` (see Sources).

The important nuance the policy forces us to get right:
- **The connection string does not disappear.** `Azure.Monitor.OpenTelemetry`
  still needs it for the **ingestion endpoint URL + the resource's
  InstrumentationKey/App-Id** (it identifies *which* resource and *where*, not
  *how* to authenticate). So `APPLICATIONINSIGHTS_CONNECTION_STRING` remains set.
- **Auth moves to the managed identity.** Set the credential and disable the
  shared-key path:
  ```csharp
  builder.Services.AddOpenTelemetry().UseAzureMonitor(o =>
  {
      // o.ConnectionString is read from APPLICATIONINSIGHTS_CONNECTION_STRING automatically.
      o.Credential = new ManagedIdentityCredential();   // Entra auth in ACA
  });
  ```
- **Disable local (key-based) auth on the component** (`DisableLocalAuth = true`
  on the `Microsoft.Insights/components` resource) and grant the `todo-api`
  managed identity the **`Monitoring Metrics Publisher`** role on that component.
  Once local auth is disabled, the InstrumentationKey embedded in the connection
  string is **no longer a usable credential** — it is just a resource identifier.
- **Therefore the connection string is non-sensitive config** and is delivered as
  a **plain env var** (NOT a Container Apps secret, NOT Key Vault). This revises
  §12.5, which had it as the `appinsights-connection` secret — that secret is no
  longer created.
- **Local dev:** leave `APPLICATIONINSIGHTS_CONNECTION_STRING` unset (exporter
  no-ops, per §12.5). Only set `o.Credential` when a connection string is present
  / when running in Azure, so `ManagedIdentityCredential` is never invoked
  locally (guard with the same environment check as §13.4, or use
  `DefaultAzureCredential`). All §12.8 tests still hold (they run with no
  connection string and no live endpoint).

### 13.6 Key Vault pattern — specified, but NOT instantiated this cycle

No current secret reaches the Key Vault branch (§13.3). We still record the
**standing pattern** so any future secret that genuinely cannot use managed
identity is handled consistently without re-litigation:

- **Resource:** one Key Vault `kv-todo-demo` (name ≤ 24 chars, globally unique —
  append `uniqueString` suffix), **RBAC authorization enabled**
  (`enableRbacAuthorization: true`) — do **NOT** use legacy vault access
  policies. Standard SKU. Soft-delete on (default), purge protection optional for
  a demo.
- **Access:** grant the consuming Container App's **system-assigned managed
  identity** the **`Key Vault Secrets User`** role (RBAC) scoped to the vault.
- **How the app reads it — Container Apps Key Vault reference (preferred).**
  Define the Container Apps secret with `keyVaultUrl` + `identity` pointing at the
  secret version; Container Apps resolves it via the app's managed identity and
  surfaces it as an env var. Rationale: no `Azure.Security.KeyVault.Secrets` SDK
  code, no startup fetch/caching logic, and rotation is handled by the platform —
  strictly simpler than reading via SDK, and it keeps secret plumbing declarative
  in Bicep. (SDK-at-startup is the documented alternative if a value must be
  fetched dynamically, which none here do.)
- **When to use:** only for a value that (a) is required by the app at runtime,
  (b) whose target service does **not** support Entra/managed-identity auth, and
  (c) therefore must be stored. Adding such a secret in a future cycle triggers:
  provision `kv-todo-demo`, grant `Key Vault Secrets User`, add the Key Vault
  reference — and record it in architecture-memory.

## 14. Entra-only Postgres authentication for the application (extension — **this cycle's scope**)

**Cycle date:** 2026-08-06. **Branch:** `pipeline/entra-passwordless-connection-string`.

> **§14 SUPERSEDES §13.4** for how the application authenticates to PostgreSQL and
> how its connection string is supplied, and **supersedes §6.2/§6.3** for local
> development database auth. It also supersedes the `UsePeriodicPasswordProvider`
> code sketch in §13.4 (already replaced in code by `UsePasswordProvider`, commit
> `1b765fd` — see `.pipeline/deployment-lessons-learned.md` §5a). Everything else
> in §13 (managed-identity-first policy, per-secret classification, App Insights,
> the Key Vault pattern) stands unchanged. Where §13.4/§6 and §14 disagree,
> **§14 wins.**

### 14.1 Overview

Two things drive this cycle.

**(a) A live bug.** Flipping `Postgres__UseEntraAuth=true` on the deployed
`todo-api` Container App still breaks the app, now failing at data-source
construction:

```
System.NotSupportedException: When registering a password provider, a password or
password file may not be set.
   at Npgsql.NpgsqlSlimDataSourceBuilder.PrepareConfiguration()
   at TodoApi.Data.TodoDbContextRegistration.BuildEntraAuthenticatedDataSource(...)
```

Root cause: **one connection-string value is shared by two auth modes that need
different connection-string shapes, and nothing reshapes it.** The Entra path
calls `UsePasswordProvider` on whatever `ConnectionStrings:TodoDb` contains; in
production that is still the SQL-auth string (`Username=todoadmin;Password=…`),
and Npgsql refuses to combine a static password with a password provider. Even
without the password, `Username` would still be wrong (`todoadmin`, not the
managed identity's Postgres role).

**(b) A deliberate scope decision by the user** (not a discovered bug):
**the application must authenticate to PostgreSQL with Entra / managed identity
ONLY — unconditionally, in every environment, including local development.**
The `Postgres:UseEntraAuth` flag, the password code path, and every `Password=`
in application configuration are removed. There is no fallback and no dual mode
*in the application*.

**Deliberately NOT in scope (second user refinement):** the **Postgres server
keeps accepting both authentication methods**. `activeDirectoryAuth: Enabled` +
`passwordAuth: Enabled` stays exactly as it is, and the `todoadmin` administrator
login and its password remain, because the user needs out-of-band `psql`/admin
access to the server. "Entra-only" is a property of **the application's
connection**, not of the server.

Removing the branch removes the class of bug entirely: there is only one
connection-string shape, so it can never be the wrong one for the mode.

**Scope:** backend code + tests, local-dev files (`docker-compose.yml`,
`appsettings*.json`), `infra/main.bicep` env wiring, `infra/README.md` runbook,
and a documented live cutover/verification procedure. **No new Azure resources.
No Azure SKU or server-auth change. Cost delta: zero.**

### 14.3 Design decision — one unconditional Entra code path

**DECISION: `TodoDbContextRegistration.AddTodoDbContext` always builds the
Entra-authenticated `NpgsqlDataSource`. The `Postgres:UseEntraAuth` flag and the
`else` branch (`options.UseNpgsql(connectionString)` with an embedded credential)
are deleted. `ConnectionStrings:TodoDb` is passwordless in every environment.**

Retained from the previous fix (do not change): the token is supplied through
`NpgsqlDataSourceBuilder.UsePasswordProvider(sync, async)` backed by
`EntraTokenPasswordProvider` + `DefaultAzureCredential`, so the token is resolved
on the connection-open path. **Never** reintroduce `UsePeriodicPasswordProvider`
(lessons §5a).

Retained as defence-in-depth: the Entra path still **strips** any `Password=` /
`Passfile=` it is handed (14.5). This is what makes the crash in 14.1(a)
structurally impossible even if someone re-points the app at a legacy connection
string, and it makes the live cutover survivable in either order.

#### Alternatives considered and rejected

| Option | Why rejected |
|---|---|
| **Keep the flag, add a second connection string** (`ConnectionStrings:TodoDbEntra`) | Contradicts the user's Entra-only directive; duplicates host/port/db in two drift-prone places; leaves a password path alive. |
| **Keep the flag, only fix the shape** (the pre-refinement draft of this spec) | Superseded by the user's scope decision. Recorded here only so the reviewer can see it was considered. |
| **Second Container Apps secret for the Entra string** | The Entra string holds **no credential** → it must not be a secret at all (§13.2). Also inert until Bicep is re-applied, which never happens. |
| **Local dev keeps a password "just for localhost"** | Explicitly rejected by the user: no silent password fallback anywhere. See 14.6. |
| **Discover the MI's Postgres role name at runtime (IMDS)** | The role name is a Postgres-side choice (whatever `pgaadauth` registered); IMDS cannot report it. The connection string is the source of truth. |

### 14.4 Configuration contract (authoritative — engineer and devops both bind to this)

**Exactly one DB configuration value remains.**

| Config key | Env var | Required | Meaning |
|---|---|---|---|
| `ConnectionStrings:TodoDb` | `ConnectionStrings__TodoDb` | **yes, every environment** | Passwordless Npgsql connection string. `Username=` **must** be the Postgres role name that maps to the caller's Entra identity (in Azure: the `todo-api` managed identity's `pgaadauth` role; locally: the local role — see 14.6). It must contain **no** `Password=` and no `Passfile=`. Non-secret → always a **plain env var / plain appsettings value**, never a Container Apps secret, never Key Vault. |

**Keys REMOVED this cycle — delete every occurrence:**

| Removed | Where it must be deleted |
|---|---|
| `Postgres:UseEntraAuth` (`Postgres__UseEntraAuth`) | `TodoDbContextRegistration.UseEntraAuthKey` const + branch; `backend/src/TodoApi/appsettings.json` (`"Postgres": { "UseEntraAuth": false }` — remove the whole `Postgres` section if it becomes empty); the `Postgres__UseEntraAuth` env var in `infra/main.bicep`; the live Container App (14.9); every mention in `infra/README.md` and code comments (incl. `Program.cs` line ~16-17). |
| `Password=` / `Passfile=` in any app config | `backend/src/TodoApi/appsettings.Development.json`; `docker-compose.yml`; `infra/main.bicep` (already absent); the live `todo-db-connection` secret (retired in 14.9). |

**No new configuration keys are introduced.** (An earlier draft of this spec
proposed `Postgres:EntraUsername`; it is **not** part of the final design — with a
single unconditional path the connection string is the only source of truth.)

**Not removed (out of app scope, per the user's refinement):** the Bicep
`postgresAdminUser` / `@secure() postgresAdminPassword` parameters, the
`todoadmin` login, the `PGADMIN_PASSWORD` CI/CD secret, and `passwordAuth:
'Enabled'` on the server. These are **deploy-time / human-admin** credentials
(§13.9), not application runtime credentials, and the user explicitly requires
continued `psql`/admin access. Leave them exactly as they are.

### 14.5 Required backend behavior

File: `backend/src/TodoApi/Data/TodoDbContextRegistration.cs`.

**Structure after the change:**

```csharp
public static IServiceCollection AddTodoDbContext(
    this IServiceCollection services, IConfiguration configuration)
{
    var connectionString = configuration.GetConnectionString("TodoDb");
    if (string.IsNullOrWhiteSpace(connectionString))
        throw new InvalidOperationException(/* existing message, keep */);

    // Entra / managed-identity auth is the ONLY supported mode (specs §14).
    services.AddSingleton(sp => BuildEntraAuthenticatedDataSource(
        connectionString,
        new DefaultAzureCredential(),
        sp.GetService<ILoggerFactory>()?.CreateLogger("TodoApi.Data.TodoDbContextRegistration")));
    services.AddDbContext<TodoDbContext>((sp, options) =>
        options.UseNpgsql(sp.GetRequiredService<NpgsqlDataSource>()));

    return services;
}
```

- The missing/blank connection-string guard and its message are **unchanged**
  (an existing test asserts it).
- `UseEntraAuthKey` is deleted. `EntraTokenPasswordProvider` is **unchanged**.
- The `NpgsqlDataSource` registration stays **lazy** (factory delegate), so merely
  calling `AddTodoDbContext` performs no credential or network work — the existing
  test factory relies on this (14.10).

**Connection-string normalization.** Implement as a **pure, `internal static`,
side-effect-free** function so it is unit-testable with no Azure, token, or DB:

```csharp
internal static string BuildEntraConnectionString(string baseConnectionString, out NormalizationReport report);
// or return a small record; the engineer may choose the shape. The rules below are binding.
```

Steps, in this exact order, using `NpgsqlConnectionStringBuilder` (do **not**
hand-roll parsing — keyword aliases and quoting must be handled):

1. **Parse.** `var b = new NpgsqlConnectionStringBuilder(baseConnectionString);`
   If it throws, surface it wrapped in an `InvalidOperationException` naming
   `ConnectionStrings:TodoDb`.
2. **Strip any static credential.** Set `b.Password = null` **and**
   `b.Passfile = null`. Both are required: Npgsql's `PrepareConfiguration()`
   rejects a password provider when *either* is set (the literal exception text is
   "a password **or password file** may not be set"). Record whether either was
   present, for the warning in step 6. Setting `b.Password = null` covers the
   `Password=` / `password=` / `pwd=` aliases because the builder normalizes them.
3. **Validate the principal.** If `b.Username` is null/whitespace, throw
   `InvalidOperationException`:
   *"ConnectionStrings:TodoDb must specify Username= — the Postgres role that maps
   to this application's Entra identity (in Azure, the todo-api managed identity's
   role). Postgres authentication for this application is Entra-only (specs §14)."*
   Do **not** guess a default and do **not** blacklist `todoadmin` by name — a
   wrong username is surfaced by the startup log (step 6), not by a heuristic.
4. **Guarantee TLS for non-loopback hosts.** The Entra access token is transmitted
   in the cleartext-password field, so the transport must be encrypted against a
   remote server. If `b.Host` is **not** a loopback host (`localhost`,
   `127.0.0.1`, `::1`, case-insensitive) **and** the resolved `b.SslMode` is
   `Disable` or `Allow`, set `b.SslMode = SslMode.Require` and flag it for a
   warning. Loopback hosts are left untouched (the local dev container has no TLS
   — 14.6). Any other `SslMode` value (`Prefer`, `Require`, `VerifyCA`,
   `VerifyFull`) is left exactly as configured. Do not touch
   `Trust Server Certificate` or anything else.
5. **Preserve everything else verbatim** — `Host`, `Port`, `Database`,
   `Trust Server Certificate`, pooling/timeout settings, and any keyword we do not
   know about must survive the round-trip unchanged.
6. Return `b.ConnectionString`, then build the data source from the **normalized**
   string with `UsePasswordProvider(provider.GetPassword, provider.GetPasswordAsync)`.

**Startup logging (required — this is the diagnosability requirement).** Emitted
once, when the `NpgsqlDataSource` singleton is constructed, via the injected
`ILogger` (category `TodoApi.Data.TodoDbContextRegistration`); all logging must be
null-safe so tests may pass `null`:

- `Information`: `"Postgres auth: Entra / managed identity. Host={Host} Database={Database} Username={Username}"`.
- `Warning` (only if it happened): `"A static Postgres password/passfile was present in ConnectionStrings:TodoDb and has been ignored — this application authenticates with Entra only (specs §14). Remove the credential from configuration."`
- `Warning` (only if it happened): `"Postgres SslMode was {Original}; forced to Require for host {Host} because the Entra token is transmitted as a cleartext password."`
- **Never** log the token, the password, or the full connection string.

**Also update the surrounding prose/comments** so nothing still claims a dual-mode
design: the class XML doc, the `BuildEntraAuthenticatedDataSource` XML doc (its
"the baseConnectionString must NOT contain a `Password=`" precondition is now
*enforced by the method*, not assumed of the caller), and `Program.cs` line ~16-17
("Uses password auth by default; managed-identity (Entra) auth when
`Postgres__UseEntraAuth=true`") → "PostgreSQL DbContext. Entra / managed-identity
auth only (specs §14)."

### 14.6 Local development — Entra-only, no password (supersedes §6.2/§6.3)

Local Postgres in Docker cannot validate Entra tokens, but the requirement is
"no password path anywhere," not "the local server must do Entra." The resolution:
**the local Postgres container is configured to require no credential at all
(`trust` authentication), so the single Entra code path runs unmodified against
it.** No `POSTGRES_PASSWORD`, no `Password=` in any file, no branch in the app.

**`docker-compose.yml` — change the `db` service to:**

```yaml
services:
  db:
    image: postgres:16
    environment:
      POSTGRES_USER: todo
      POSTGRES_DB: tododb
      # Entra-only application auth (specs §14.6): this local container cannot
      # validate Entra tokens, so it is configured to require NO credential at
      # all. This keeps a single, unconditional Entra code path in the app with
      # zero passwords anywhere. Local-only; never used in Azure.
      POSTGRES_HOST_AUTH_METHOD: trust
    ports:
      - "5432:5432"
    volumes:
      - todo_pgdata:/var/lib/postgresql/data
```

`POSTGRES_PASSWORD` is **deleted**. `POSTGRES_USER` stays `todo` to minimise churn.

**`backend/src/TodoApi/appsettings.Development.json`:**

```json
"ConnectionStrings": {
  "TodoDb": "Host=localhost;Port=5432;Database=tododb;Username=todo;Ssl Mode=Disable"
}
```

(no `Password=`; `Ssl Mode=Disable` is fine and is preserved by 14.5 step 4
because `localhost` is loopback).

**`backend/src/TodoApi/appsettings.json`:** delete the `"Postgres": { "UseEntraAuth": false }`
section; leave `"ConnectionStrings": { "TodoDb": "" }` as-is.

**Developer prerequisites — document in `README`/§6.3 run instructions:**
1. **`docker compose down -v` once** before the first `up` after this change.
   `POSTGRES_HOST_AUTH_METHOD` is only honoured by `initdb` on an **empty** data
   directory; an existing `todo_pgdata` volume keeps its old `scram-sha-256`
   `pg_hba.conf` and will still demand a password. This wipes local todo data
   (local only, no production impact).
2. **`az login` once per machine.** `DefaultAzureCredential` resolves to
   `AzureCliCredential` locally. Under `trust` the server never challenges for a
   password, so Npgsql should never need to invoke the provider — but this must
   not be left to chance.
   **Engineer action:** verify empirically whether Npgsql invokes the password
   provider when the server replies `AuthenticationOk` immediately, and record the
   observed behaviour in `.pipeline/changes.md`. If the provider **is** invoked
   eagerly, `az login` is a hard local prerequisite; if it is not, `az login` is
   only needed for developers who also connect to Azure resources. Either way the
   documented instruction is "run `az login` once" — this is the accepted cost of
   Entra-only.

**Tradeoff (documented, as required).** `trust` means the local container accepts
any connection on the mapped port with no credential. Accepted because: it is a
throwaway local container with demo data, it is already published only to
`localhost`, and it is the only way to keep one code path with zero passwords.
Developers who consider this unacceptable on a shared machine should not publish
port 5432 (drop the `ports:` mapping and run the backend inside the compose
network) rather than reintroducing a password.

**Alternative considered and rejected — point local dev at the real Azure server**
using the developer's own Entra identity (`az login` + `Username=<dev UPN>`):
rejected because it needs a per-developer Postgres firewall rule (lessons §4a),
a `pgaadauth` principal per developer, gives every developer write access to the
demo database (and the startup `Migrate()` would run against it), and breaks
offline work. It remains the right tool for *manually* verifying real Entra
behaviour, and is documented as such in 14.7, not as the everyday loop.

### 14.9 Live cutover / verification procedure (human-run, after merge)

Lessons §5a: mocked tests cannot prove this works; a live check is mandatory.
**There is no in-app fallback any more — the rollback is revision-level**, which
works because the previous revision (old image + `todo-db-connection` secret) is
untouched and the server still accepts password auth (14.8 item 2).

```bash
RG=rg-todo-demo
APP=todo-api
PG_FQDN=pg-todo-demo-cus01.postgres.database.azure.com

# 0. PRE-CHECK — confirm the in-DB principal exists and matches the OID (14.7). Do not skip.

# 1. Record the current (known-good) revision name so rollback is one command.
PREV_REV=$(az containerapp revision list -g $RG -n $APP \
  --query "[?properties.active]|[0].name" -o tsv); echo "rollback target: $PREV_REV"

# 2. Let CD deploy the new image, then confirm the running revision actually has it.
az containerapp revision list -g $RG -n $APP \
  --query "[?properties.active].{rev:name,image:properties.template.containers[0].image}" -o table

# 3. Replace the connection string with the passwordless value and drop the dead flag.
#    --set-env-vars replaces that variable's definition (secretRef -> plain value)
#    and leaves all other env vars alone. The todo-db-connection SECRET is NOT
#    deleted here — it stays as part of the rollback revision.
az containerapp update -g $RG -n $APP \
  --set-env-vars "ConnectionStrings__TodoDb=Host=$PG_FQDN;Port=5432;Database=tododb;Username=todo-api;Ssl Mode=Require;Trust Server Certificate=true" \
  --remove-env-vars Postgres__UseEntraAuth

# 4. Verify health AND a DB-backed endpoint (/health alone does not touch the DB).
API_FQDN=$(az containerapp show -g $RG -n $APP --query properties.configuration.ingress.fqdn -o tsv)
curl -fsS "https://$API_FQDN/health"
curl -fsS "https://$API_FQDN/api/todos"      # must return 200 + a JSON array, not 500

# 5. Confirm the startup log shows the right principal and no stripped credential.
az containerapp logs show -g $RG -n $APP --tail 100 | grep -i "Postgres auth"
#    EXPECT: "Postgres auth: Entra / managed identity. Host=pg-todo-demo-cus01... Username=todo-api"
#    EXPECT: no "static Postgres password/passfile ... ignored" warning (step 3 removed it)

# 5b. ROLLBACK (only if 4 or 5 fails):
#     az containerapp revision activate -g $RG -n $APP --revision "$PREV_REV"
#     (old image + old secretRef env; still works because the server keeps password auth)

# 6. CLEANUP — only after at least one healthy revision on Entra auth (see Q1):
#     az containerapp secret remove -g $RG -n $APP --secret-names todo-db-connection
```

Note that steps 2 and 3 may be done in either order thanks to the normalization in
14.5 — a new image reading the old password-bearing secret strips the credential
and then fails auth as `todoadmin` (a clean, logged auth error), rather than
crashing with `NotSupportedException`. Doing step 2 first is still preferred.

**Success criteria:** `/api/todos` returns 200; the `Information` log shows
`Username=todo-api`; no `NotSupportedException`, no `28P01`, no
`"No password has been provided"` in the logs; traces still land in
`appi-todo-demo`. Afterwards, the outcome **must** be written back into
`.pipeline/infra.md` and `.pipeline/deployment-lessons-learned.md` §5a — that
entry is currently marked UNRESOLVED and must be closed out with the real result.

  token, or full connection string is ever logged.
- **Scaling / performance:** unchanged. Normalization happens once, at singleton
  construction — not per connection, not per request.
- **Availability:** the startup `Migrate()` runs as the MI's Postgres role.
  Migration failures are still caught and logged without crashing the app
  (`Program.cs`), so `/health` stays up and diagnosable. Rollback is
  revision-level (14.9).
- **Cost:** zero delta. No new resources, no SKU change.
- **Region:** unchanged — ACA in `eastus`, Postgres in `centralus`
  (`pg-todo-demo-cus01`; forced by the subscription restriction in lessons §1a).
  Do not "fix" this mismatch.
- **Breaking change:** yes, and deliberately so. Any environment still supplying a
  `Password=`-bearing connection string will have the credential ignored (with a
  warning) and will then fail authentication unless `Username=` names a valid
  Entra-mapped role. This is the intended consequence of the user's directive and
  must be called out in `changes.md`.

### 14.12 Out of scope (explicitly)

- **Disabling `passwordAuth` on the Postgres server, or removing the `todoadmin`
  login / `postgresAdminPassword` parameter / `PGADMIN_PASSWORD` CI secret.**
  Explicitly excluded by the user — human admin access must keep working.
- Making the server Entra-authentication-only, or dropping the `todoadmin` role
  in-database.
- Key Vault (§13.6) — still not instantiated; nothing here is a secret.
- Changing `EntraTokenPasswordProvider`, the token scope, or reverting to
  `UsePeriodicPasswordProvider`.
- App Insights / tracing (§12, §13.5), frontend, API surface, data model, EF
  migrations content, CI/CD workflow logic, and any new Azure resource.
- Per-developer Entra principals on the shared Azure Postgres server (14.6
  rejected alternative).
- Automating the `pgaadauth` bootstrap — it stays human-run (§11.6, 14.7).

### 14.13 Assumptions, risks and open questions

**Assumptions (decided; implement against these):**
1. The managed identity's Postgres role name is **`todo-api`** — Container App
   name == system-assigned identity display name == `pgaadauth` role name ==
   `Username=`. Confirmed live (14.2). One source of truth; a mismatch fails auth.
2. The in-DB principal and `tododb` grants from Phase 4 step B are still present;
   14.7 is a *verification*, not a re-run.
3. `POSTGRES_HOST_AUTH_METHOD: trust` on `postgres:16` makes the local server
   accept connections with no credential, so the single Entra path works locally.
   It only takes effect on a **fresh** data directory (hence `down -v`).
4. Stripping (rather than rejecting) a `Password=` in configuration is correct:
   it makes the `NotSupportedException` structurally impossible and makes the
   cutover order-independent. The `Warning` log is the guard against it hiding a
   real misconfiguration.
5. Fail-fast on a missing `Username=` is better than attempting a connection that
   would fail with an opaque Postgres `28P01`.

**Risks to state in `changes.md`:**
- **No in-app fallback.** If the Entra path breaks in Azure, recovery is a
  revision rollback (or a code change), not a config flag. Mitigated by: the
  server keeping password auth, the previous revision remaining intact, and 14.9
  capturing the rollback command *before* the cutover.
- **`az login` may become a hard local prerequisite** (14.6 item 2) — a one-time
  per-machine cost, and the accepted price of Entra-only.
- **`trust` on the local container** weakens local-only security; mitigation
  documented in 14.6.

**Open questions (do not block implementation):**
- **Q1.** How long before deleting the `todo-db-connection` secret (14.9 step 6)?
  *Recommendation:* after at least one healthy Entra revision has served real
  traffic; never in the same change as the cutover.
- **Q2.** Should CD assert the app's env/connection-string shape (drift
  detection), now that CD never applies Bicep? *Recommendation:* worth a follow-up
  cycle given lessons §2c/§2d; out of scope here.
- **Q3.** Should local dev eventually move to a Postgres image with a token-
  validating auth shim so local and Azure are truly identical? *Recommendation:*
  no — cost/complexity far exceeds the benefit for a demo; revisit only if local
  auth drift causes a real defect.

## 16. Authentication & authorization — Microsoft Entra External ID + Postgres roles (extension — **this cycle's scope**)

**Cycle date:** 2026-08-12. **Branch:** `pipeline/entra-external-id-auth`.

> **Section numbering:** §15 (dev environment + dev→prod promotion) is authored and
> validated on the unmerged branch `pipeline/dev-environment` (commit `37f8aa5`,
> paused on a Container Apps Environment quota limit). That number is **reserved**;
> this cycle is **§16** so the two can merge without renumbering. §16 assumes the
> current single (production) environment. Where §15 later lands, everything in §16
> must be duplicated per environment — see 16.14.
>
> **§16 does NOT supersede §14.** The application's PostgreSQL connection stays
> Entra/managed-identity-only, passwordless, plain env var, zero fallback. §16 adds
> *application-level* authentication of **end users** and authorization on top of it.
> Nothing about the *transport* to Postgres changes. Where §16 and §13/§14 appear to
> disagree about secrets, see **16.6**, which reconciles them explicitly.

### 16.1 Overview

The Todo app is currently anonymous: anyone who can reach `todo-web` can read and
mutate every todo through `todo-api`, which accepts unauthenticated requests
(specs §8, "No auth", was an explicit initial out-of-scope item). This cycle
closes that: end users **self-register and sign in** through a new **Microsoft
Entra External ID** (CIAM) tenant — either with an email + password local account
(collecting name and phone at sign-up) or with a **Google** account federated into
the same sign-in page — and every `todo-api` request must now carry a valid
Entra-issued access token. **Entra proves *who* the caller is; PostgreSQL decides
*what they may do*:** a new `users` table maps each Entra object ID to a profile
and exactly one of two roles, `User` or `Admin`, and a server-side claims
transformation re-derives that role from the database on **every** request before
authorization runs. The SPA gains MSAL (silent SSO on load, interactive fallback,
a "Continue with Google" shortcut) and hides admin-only routes, while the API
enforces them.

**Scope:** backend (token validation, claims transformation, provisioning, users
endpoints, EF migration), frontend (MSAL, routing, role-aware UI), one new Azure
resource (**Key Vault**, custodial — see 16.6), Bicep + workflow env/build-arg
wiring, and a large **human-run bootstrap** in the external tenant, Google Cloud,
and Postgres. **No change to compute topology, SKUs, regions, or the Postgres
server.**

### 16.4 Data model

#### 16.4.1 Table `users`

Storage choice: the **existing** `tododb` PostgreSQL Flexible Server / `public`
schema. No new database, server, or store. Created by an **EF Core code-first
migration** (§3.4 convention), applied by the existing startup `Migrate()` running
as the `todo-api` pgaadauth role.

| Column | Type | Constraints | Notes |
|---|---|---|---|
| `id` | `uuid` | PK | Internal surrogate key, generated in C# (`Guid.NewGuid()`), matching the `todos` pattern. Never exposed to Entra. |
| `entra_object_id` | `uuid` | **NOT NULL, UNIQUE** | The token's **`oid`** claim. The join key between Entra and this table. |
| `email` | `text` | NULL | From the `email` / `preferred_username` claim when present. Informational only — **never** used for authorization. |
| `display_name` | `text` | NULL | `name` claim, else `given_name + ' ' + family_name`. |
| `phone_number` | `text` | NULL | From the phone custom-attribute claim (16.5.4) when present; otherwise user-supplied via `PUT /api/users/me`. |
| `role` | `text` | **NOT NULL**, default `'User'`, `CHECK (role IN ('User','Admin'))` | The single source of truth for authorization. |
| `created_at` | `timestamptz` | NOT NULL | Set at provisioning. |
| `updated_at` | `timestamptz` | NOT NULL | Bumped on profile/role change. |

Indexes: PK on `id`; **unique index on `entra_object_id`** (`ix_users_entra_object_id`)
— this is both the lookup path for every authenticated request and the race guard
for concurrent first-login provisioning across replicas.

Column widths: the three PII columns are Postgres `text` (unbounded) by design —
an IdP-supplied value must never be truncated or rejected at the DB layer. Bounds
are enforced at the **API** edge instead, on the only path a client can write them
(`PUT /api/users/me`): `displayName` ≤ **256** chars, `phoneNumber` ≤ **64** chars,
both via data annotations so a violation is a `400 ValidationProblemDetails`
consistent with §3.5. `role` is `text` + CHECK, never a Postgres `ENUM` (16.4.2).

**`oid`, not `sub` — this is a correctness requirement, not a preference.** The
`sub` claim in Microsoft identity platform tokens is **pairwise**: the same human
gets a *different* `sub` per application. Keying on `sub` would create a second row
for the same person as soon as a second client (or the ID token vs. the access
token) is involved, silently splitting their profile and role. `oid` is the
directory object ID: stable per user per tenant, identical across all apps in the
tenant. Use `oid`. If `oid` is absent from a validated token, that is a
misconfiguration — **reject with 401**, do not fall back to `sub`.

#### 16.4.2 Entity / EF mapping

* `TodoApi/Models/AppUser.cs` — named `AppUser` (not `User`) to avoid colliding with
  `System.Security.Claims`/ASP.NET `User` in controllers. Table name stays `users`.
* `TodoApi/Models/UserRole.cs` — `enum UserRole { User = 0, Admin = 1 }`, mapped with
  `.HasConversion<string>()` so the DB stores `'User'`/`'Admin'` (readable in psql,
  which matters for the bootstrap in 16.11). **Do not** use a Postgres `ENUM` type —
  EF migrations handle text + CHECK far more cleanly.
* `TodoDbContext` gains `DbSet<AppUser> Users`, snake_case column mapping consistent
  with the existing `todos` mapping, and the CHECK constraint via
  `ToTable(t => t.HasCheckConstraint("ck_users_role", "role IN ('User','Admin')"))`.
* Migration name: `AddUsers`. It must be additive only — **it must not touch
  `todos`**.

#### 16.4.3 Relationship to `todos` — deliberately none

`todos` gets **no `owner_id` column** and no FK to `users` in this cycle. Todos
remain a single shared list visible to every authenticated user. Per-user todo
ownership is a different feature (data migration for existing rows, per-row
authorization, list filtering, admin override semantics) and is **explicitly out of
scope** (16.15). Stating this loudly because "add auth" is usually assumed to imply
"and now todos are per-user" — it does not here, and the engineer must not add it.

#### 16.5.2 App registration — `todo-api-app` (the protected API)

* Supported account types: **Accounts in this organizational directory only**.
* **Expose an API** → Application ID URI: accept `api://<api-client-id>`.
* Add **one delegated scope**: `Todos.ReadWrite` (admin consent display name
  "Access the Todo API on behalf of the signed-in user"). Do **not** add app roles
  or application permissions — there is no daemon client, and every unused
  permission is attack surface.
* Manifest: `accessTokenAcceptedVersion = 2` (v2 tokens; `scp` claim).
* **Token configuration → optional claims (Access token):** add `email`,
  `given_name`, `family_name`, and the **directory extension** claim for the phone
  attribute (16.5.4). Where a claims-mapping edit requires it, set
  `acceptMappedClaims = true` on this registration.
* **No client secret and no certificate is created for this registration.** The API
  only *validates* tokens (public JWKS); it never *acquires* one. If anyone is about
  to create a secret here, the design has been misunderstood.

#### 16.5.3 App registration — `todo-web-spa` (the SPA)

* Supported account types: same tenant only. Platform: **Single-page application**
  (this is what enables auth code + PKCE and refuses the implicit flow).
* Redirect URIs:
  * `https://todo-web.lemoncliff-b3b8a3d9.eastus.azurecontainerapps.io/`
  * `http://localhost:5173/` — the **only** permitted non-TLS URI, allowed because
    it is strictly loopback (consistent with the §14.5 loopback exemption). Never
    register a non-loopback `http://` URI.
* API permissions: Microsoft Graph `openid`, `offline_access`, `profile`, `email`
  (delegated) + `todo-api-app` → `Todos.ReadWrite`. Then **Grant admin consent** —
  in an external tenant, end users cannot consent for themselves, so without this
  step every sign-in fails at the consent screen.
* **Public client. No secret, ever.** A secret in a SPA is a published secret.

#### 16.5.4 User flow `SignUpSignIn` and the phone attribute

* External Identities → User flows → **New user flow**, name `SignUpSignIn`.
* Identity providers: **Email Accounts → "Email with password"** (gives the
  email/password login the requirement asks for, plus self-service password reset)
  **and** Google (only selectable after 16.5.5 is done — order matters).
* User attributes to collect: **Email Address** (implicit), **Given Name**,
  **Surname**, and **`phoneNumber`**.
* **Finding — there is no built-in phone attribute.** The built-in collectable set
  in external tenants is exactly: City, Country/Region, Display Name, Email Address,
  Given Name, Job Title, Postal Code, State/Province, Street Address, Surname.
  **Phone is not in it.** So `phoneNumber` must be created first as a **custom user
  attribute** (External Identities → Custom user attributes → Add: name
  `phoneNumber`, data type **String**, input type **TextBox**), then selected in the
  user flow. It is stored as a directory extension on the `b2c-extensions-app` and
  is surfaced in tokens as
  `extension_<b2cExtensionsAppId-without-hyphens>_phoneNumber`.
  * Consequence: **the phone claim name is tenant-specific and only knowable after
    the tenant exists.** The API must not hard-code it — see 16.7.4.
  * `phoneNumber` is a free-text string, **not** a verified phone number and **not**
    an MFA method. No SMS verification in this cycle (16.15).
* **Add both applications to the user flow** (`todo-web-spa` and `todo-api-app`).
  An application can be associated with only one user flow.
* Google sign-ups: the attribute-collection page is expected to appear on the
  **first** Google sign-in for attributes the IdP does not supply (i.e. phone), with
  name/email pre-filled from Google. **Assumption A3 (16.16) — verify empirically.**
  The design degrades safely if it does not: `phone_number` is nullable and
  `PUT /api/users/me` lets the user fill it in.

### 16.6 Secrets — reconciling the user's request with §13/§14 (read this before wiring anything)

The request said: *"Create an Azure Key Vault; put the Google client secret and the
Postgres connection string in it; API's managed identity gets read permission."*
Applying that literally would **regress** two hard-won invariants. Here is the
honest accounting, per item:

**(1) The Postgres connection string — requirement does not apply. Do not put it
in Key Vault.**
Since §14 the application's connection string is **passwordless**
(`Host=…;Port=5432;Database=tododb;Username=todo-api;Ssl Mode=Require;…`) and
contains **no credential at all** — authentication happens at connection-open time
with an Entra token fetched by `todo-api`'s managed identity. It is therefore not a
secret, and §13.2/§14.4 require it to be a **plain env var**. Moving a non-secret
into Key Vault would (a) add a runtime dependency and failure mode for zero security
gain, (b) contradict §14.4's "single source of truth, plain env var" contract, and
(c) invite a future reader to "restore" a password into it. **Decision: unchanged
from §14. The DB half of requirement 3 is not applicable, by design, because the
thing it was protecting no longer exists.** The `users` table is reached over that
exact same existing `NpgsqlDataSource` — no second connection string, no second auth
path.

**(2) The Google client secret — a real secret, and the reason Key Vault is now
justified.**
It is issued by **Google**, a third party with no relationship to Entra ID. It
cannot be replaced by a managed identity, a workload-identity federation, or any
Entra construct — this is precisely the "dependency that genuinely cannot
authenticate via Entra ID" case in which Key Vault is the correct fallback. But note
*who consumes it*: **Entra External ID does**, once, at IdP configuration time. Our
applications never do.

**Decision:** provision **one Key Vault** (`kv-todo-…`, `rg-todo-demo`, eastus,
Standard, **RBAC authorization**) as the **custodial store of record** for the Google
OAuth client secret, so the value has a rotation-safe home that is not a chat
message, a sticky note, or a git-tracked file.

* Secret name: `google-oauth-client-secret`. (The Google **client ID** is not secret
  and may live in plain documentation/config if ever needed.)
* **Access model — Entra RBAC only.** `enableRbacAuthorization: true` (never legacy
  access policies). The **human operator** who administers the external tenant gets
  **`Key Vault Secrets Officer`** on the vault, granted out-of-band by a human
  (§11.6: agents never create role assignments). Access to Key Vault is itself
  Entra-authenticated via that human's Entra identity — **no vault access key, no
  SAS token, no shared credential of any kind.**
* **Deliberately: neither `todo-api`'s nor `todo-web`'s managed identity is granted
  any role on this vault.** The request asked for API read permission; the API has
  no use for this secret, and granting it would violate least privilege and create a
  path by which a compromised API could exfiltrate the Google credential. **This is a
  documented, intentional deviation from the literal request.**
* Secrets are written by a human (`az keyvault secret set --vault-name <kv> --name
  google-oauth-client-secret --value <paste>`), never by an agent, never by CI/CD.
* Purge protection: `enableSoftDelete: true`, `softDeleteRetentionInDays: 7`,
  `enablePurgeProtection: false` — soft delete gives recoverability; purge protection
  is irreversible and unnecessary for a demo (documented tradeoff, revisit for prod).
* Cost: ~$0.03 per 10,000 operations, and this vault sees a handful of operations per
  *year*. Effectively **$0/month**.

**(3) Everything else stays secretless.** Neither app registration has a client
secret (the SPA is a public client with PKCE; the API only validates tokens). The
external tenant IDs, client IDs, authority URLs and scope names are **public
identifiers**, not credentials — they ship in the SPA bundle by necessity and are
plain env vars on the API.

**If a future feature needs the app to read a Key Vault secret**, the mandatory
pattern is still §13.6: Container Apps Key Vault *reference* secret
(`keyVaultUrl` + `identity: system`), with `Key Vault Secrets User` granted to the
Container App's managed identity — Entra-authenticated, never a vault key. Record any
such secret in `architecture-memory.md`.

**Net effect on the §13 per-secret classification table:** unchanged for every
existing row; **one new row** — *Google OAuth client secret → consumed by Entra
External ID, custodied in Key Vault, read by humans only, never by an application.*
**Application runtime secrets remain: zero.**

remove. `/health` must still respond (see 16.7.7).

validation parameter: it is the value the `[RequiredScope]` enforcement in 16.7.2a

security downgrade. (An earlier draft of this section listed only four keys; the
five-key list above is authoritative.)

  outright; token metadata is always fetched over TLS (16.10).
* `TenantId` must parse as a **GUID**.

`Users:PhoneClaimName` is optional and must **never** be part of the fail-fast
list: its value cannot be known until the external tenant exists (16.5.4).

#### 16.7.2 Token validation

```csharp
builder.Services
    .AddAuthentication(JwtBearerDefaults.AuthenticationScheme)
    .AddMicrosoftIdentityWebApi(builder.Configuration.GetSection("AzureAd"));
```

Binding requirements (assert these explicitly in code where they are not already the
framework default, and cover them with tests):

* `RequireHttpsMetadata = true` (default — **never** set false).
* `ValidateIssuer = true`, `ValidateAudience = true`, `ValidateLifetime = true`,
  `ValidateIssuerSigningKey = true`. **Never** set any of these to false, and never
  supply a custom `IssuerValidator` that returns unconditionally.
* Audience = `api://<api-client-id>` (and/or the bare client ID). This is what makes
  an **ID token** (audience = the SPA's client ID) unusable against the API — a
  common and serious bypass if audience validation is loose.
* `ClockSkew` — leave the default (5 min).

**Known External ID issuer gotcha (call this out to the engineer).** The
configured authority uses the *subdomain* host
(`https://<sub>.ciamlogin.com/<tenantId>/v2.0`) while the token's `iss` uses the
*tenant GUID* host (`https://<tenantId>.ciamlogin.com/<tenantId>/v2.0`).
`Microsoft.Identity.Web`'s issuer validator is expected to accept this via the
discovery document's `issuer` template — **verify against a real token during
implementation**. If it fails with `IDX10205`, the **only** acceptable fix is to add
both concrete issuer strings to `TokenValidationParameters.ValidIssuers` via a
`Configure<JwtBearerOptions>` post-configuration step. **Disabling issuer validation
is not an acceptable fix** and must be rejected in review.

Additionally, as defence in depth, the claims transformation (16.7.3) **must** verify
that the `tid` claim equals `AzureAd:TenantId` and fail the request otherwise.

#### 16.7.2a Scope enforcement — required, and required *everywhere*

Audience validation proves the token was minted **for this API**; it does not prove
the user consented to the delegated permission. §16.8 requires `scp` to contain
`Todos.ReadWrite` on **every non-anonymous endpoint**, so state the mechanism
explicitly rather than leaving it to each controller author:

* Use `Microsoft.Identity.Web`'s **`[RequiredScope(RequiredScopesConfigurationKey =
  "AzureAd:Scopes")]`** — bound to configuration, never a hard-coded literal.
* It must be applied to **`UsersController` *and* `TodosController`**. A partial
  application is a real gap: a token issued for this audience but without the
  scope would still reach `/api/todos`. `TodosController` therefore changes in
  this cycle — **attributes only**; its routes, DTOs and payloads are untouched
  (the §3.5 contract still holds for authenticated callers).
* Any future controller inherits authentication from the fallback policy but
  **not** the scope check, so adding `[RequiredScope(...)]` alongside the class-
  level `[Authorize]` is part of "adding a controller" in this codebase. Reviewers
  must check for it.
* Insufficient scope ⇒ **`403`** (`insufficient_scope`), not `401` — the caller is
  authenticated, just not permitted.
* `/health` is `[AllowAnonymous]` and carries no scope requirement (16.7.7).

#### 16.7.3 Role attachment — `RoleClaimsTransformation` (Entra proves identity, Postgres decides role)

Implement `TodoApi/Auth/RoleClaimsTransformation.cs` as an `IClaimsTransformation`,
registered **scoped** (it needs the request-scoped `TodoDbContext`). It runs after
token validation and before authorization, on every authenticated request.

Required behaviour, in order:

1. If the principal is not authenticated, return it untouched.
2. **Idempotence guard.** `IClaimsTransformation.TransformAsync` may be invoked more
   than once per request. If the identity already carries our marker
   (`todo:role_source == "db"`), return immediately — no second DB round trip.
3. Read `tid`; if it is missing or ≠ `AzureAd:TenantId`, **do not** add any role and
   mark the principal as rejected (the endpoint filter/handler returns 401). A token
   from another tenant that somehow passed signature validation must not become a
   local user.
4. Read `oid` (`http://schemas.microsoft.com/identity/claims/objectidentifier` or
   `oid`). Missing/unparseable as a GUID ⇒ same rejection as (3). **Never fall back
   to `sub`, `email`, or `preferred_username` as the identity key.**
5. **Strip every inbound role claim** — all claims whose type is `roles`, `role`, or
   `ClaimTypes.Role` — from the cloned identity **before** adding ours. Today the
   tenant issues none; this makes it structurally impossible for a future app-role
   assignment, a claims-mapping change, or a mis-scoped token to grant `Admin`.
6. **Get-or-create** the `users` row (16.7.5) and read its `role`.
7. Add exactly one role claim, using the identity's own `RoleClaimType`
   (`((ClaimsIdentity)principal.Identity).RoleClaimType`) so that both
   `User.IsInRole(...)`, `[Authorize(Roles = "Admin")]` and policy-based checks
   agree regardless of how MIW configured the mapping. Add the
   `todo:role_source = "db"` marker claim.
8. Return a **cloned** `ClaimsPrincipal` (never mutate the validated identity in
   place).

Authorization policies, registered in `Program.cs`:

```csharp
builder.Services.AddAuthorization(options =>
{
    options.FallbackPolicy = new AuthorizationPolicyBuilder()
        .RequireAuthenticatedUser()
        .Build();                                   // secure by default
    options.AddPolicy("AdminOnly", p => p.RequireRole("Admin"));
});
```

The **fallback policy** is deliberate: any endpoint added in the future is
authenticated unless someone *explicitly* writes `[AllowAnonymous]`. The alternative
(remembering to add `[Authorize]` to each new controller) is the classic way auth
silently regresses.

**Rejected alternatives (record in review):**

| Alternative | Why rejected |
|---|---|
| Put the role in an Entra **app role** / group claim | The API would have to *write* roles into the external tenant to promote a user — i.e. Graph write access from `todo-api`. Its managed identity lives in the **workforce** tenant and cannot authenticate to the external tenant, so this would require an app registration **with a client secret** in the external tenant: a new stored application secret, directly contradicting §13/§14. Postgres-held roles keep the zero-secret posture. It also contradicts the explicit requirement ("Postgres decides permissions"). |
| Trust a role claim the SPA sends (header/body/localStorage) | Trivial privilege escalation. The client is never authoritative for authorization. |
| Cache the role in the token (only re-read at login) | A demotion would not take effect until the token expires (up to ~1 h). Re-deriving per request makes revocation immediate. |
| Custom middleware instead of `IClaimsTransformation` | Would have to run after `UseAuthentication` and re-implement principal replacement; `IClaimsTransformation` is the framework-sanctioned hook and composes with `[Authorize(Roles=…)]` for free. |
| In-memory role cache | Deferred, not rejected: correctness first. A short (30–60 s) `IMemoryCache` keyed by `oid` is the documented optimisation **if** the per-request indexed lookup ever shows up in traces; it trades immediate revocation for latency and must be a conscious, documented change. |

#### 16.7.4 Reading the profile claims

* `email` ← `email`, else `preferred_username` (if it looks like an email).
* `display_name` ← `name`, else `"{given_name} {family_name}".Trim()`, else null.
* `phone_number` ← the claim named by `Users:PhoneClaimName` when configured;
  otherwise **the first claim whose type ends with `_phoneNumber`** (this survives
  the tenant-specific `extension_<appId>_phoneNumber` naming from 16.5.4 without
  hard-coding a GUID). If neither is found, leave it null — this is normal, not an
  error, and must not fail the request.
* All three are **informational profile data only**. None of them may influence
  authorization in any way.

#### 16.7.5 First-login provisioning — get-or-create inside the transformation

**Decision: the profile row is created lazily, server-side, on the first
authenticated request, inside the same code path that reads the role. There is no
`/api/auth/provision` endpoint.**

Mechanism (`TodoApi/Auth/UserProvisioningService.cs`):

```
row = SELECT * FROM users WHERE entra_object_id = @oid
if (row == null):
    INSERT users(id, entra_object_id, email, display_name, phone_number,
                 role, created_at, updated_at)
    VALUES (newGuid, @oid, @email, @name, @phone, 'User', now, now)
    on unique-violation (23505, concurrent replica):
        row = SELECT ... again      // the other request won; use its row
return row
```

* `role` is **always** the server-side literal `'User'` on insert. It is never read
  from the request, the token, or configuration. There is **no "first user becomes
  Admin"** rule — that is a land-grab race (whoever registers first, including an
  attacker, becomes Admin). Bootstrap is a deliberate human DB action (16.11).
* The unique index on `entra_object_id` plus the 23505 catch makes this safe across
  the up-to-3 `todo-api` replicas.
* Existing rows: only `updated_at`-worthy profile drift is ignored here (a returning
  user's changed name is not re-synced on every request — that would make every
  request a write). `PUT /api/users/me` is the update path.
* Log at `Information` **once per creation**: `"Provisioned new user {Oid} with role
  User."` — log the `oid` only. **Never** log the token, email, or phone.

**Rejected alternative — `POST /api/auth/provision` called by the SPA after login.**
It is skippable: any authenticated caller (curl, a second client, a returning user
whose SPA call failed) could reach `/api/todos` with no row, so every other endpoint
would need a "row missing" fallback anyway — i.e. we would implement get-or-create
regardless, plus an extra endpoint and an extra round trip. It also puts a
client-triggered write on the auth path. Lazy server-side provisioning has exactly
one code path and cannot be bypassed. (Cost: the auth path touches the DB on every
request; accepted, see 16.14.)

#### 16.7.6 Middleware order

```
UseCors(CorsPolicyName)      // MUST stay first: answers preflight before auth,
                             // and puts CORS headers on 401/403 so the browser
                             // surfaces a real status instead of an opaque failure
UseAuthentication()
UseAuthOutcome()             // AuthOutcomeMiddleware — see below. Between
                             // UseAuthentication() and UseAuthorization().
UseAuthorization()
MapGet("/health").AllowAnonymous()
MapControllers()
```

**`AuthOutcomeMiddleware` — why it exists and what it must do.** `RequireAuthenticatedUser()`
is satisfied by *any* validated token. A principal that carried the wrong `tid`, or
no usable `oid`, or whose role could not be read from Postgres, is still
"authenticated" — it just has no role — so without this middleware it would sail
past the fallback policy and be refused (or, worse, allowed) somewhere further in,
inconsistently. The transformation therefore **marks** such principals
(`todo:auth_failure`, 16.7.1a) instead of throwing, and this middleware converts the
marker into a response **before authorization runs**:

| `todo:auth_failure` value | Status | Body |
|---|---|---|
| `invalid_principal` (wrong `tid`, missing/unparseable `oid`) | **401** + `WWW-Authenticate: Bearer` | `ProblemDetails`, generic — never echo the claim, the token, or which check failed in detail |
| `role_source_unavailable` (Postgres unreachable) | **503** | `ProblemDetails`, "Authorization data is temporarily unavailable. Please retry." |

Rules:
* Endpoints carrying `IAllowAnonymous` metadata (only `/health`) are **skipped**, so
  a caller presenting a broken token can never take the health probe down.
* Log a `Warning` for a refused authenticated caller with **path + method only** —
  never the token, the `Authorization` header, or any claim value (16.10).
* This middleware is the **only** place that maps an auth-outcome marker to a
  status. Do not duplicate the mapping in controllers or filters.

#### 16.7.7 `/health` stays anonymous

`GET /health` keeps returning `{ "status": "ok" }` with **no** token required —
Container Apps probes cannot present one, and gating it would take the app down.
With the fallback policy in place this now requires an explicit `.AllowAnonymous()`.
It must not leak anything: no user counts, no config, no claim echo. It also must not
touch the DB (unchanged from today).

### 16.8 API surface

All endpoints are HTTPS-only (ACA ingress) and, except `/health`, require
`Authorization: Bearer <access token>` with `scp` containing `Todos.ReadWrite`.

| Method | Path | Auth | Behaviour |
|---|---|---|---|
| GET | `/health` | **Anonymous** | Unchanged: `{ "status": "ok" }` |
| GET | `/api/todos` | Authenticated | Unchanged payload |
| GET | `/api/todos/{id}` | Authenticated | Unchanged |
| POST | `/api/todos` | Authenticated | Unchanged |
| PUT | `/api/todos/{id}` | Authenticated | Unchanged |
| DELETE | `/api/todos/{id}` | Authenticated | Unchanged |
| GET | `/api/users/me` | Authenticated | **NEW** — the caller's provisioned profile + role |
| PUT | `/api/users/me` | Authenticated | **NEW** — self-service profile update (`displayName`, `phoneNumber` only) |
| GET | `/api/users` | **AdminOnly** | **NEW** — list all users (demo scale: unpaged, ordered by `created_at`) |
| PATCH | `/api/users/{id}/role` | **AdminOnly** | **NEW** — promote/demote |

**Shapes** (camelCase JSON, consistent with existing DTOs):

```jsonc
// GET /api/users/me  → 200
{
  "id": "b0a1…",                 // internal uuid
  "entraObjectId": "7f3c…",      // oid
  "email": "<user@example.com>",
  "displayName": "<name>",
  "phoneNumber": "<phone or null>",
  "role": "User",                // "User" | "Admin"
  "createdAt": "2026-08-12T10:00:00Z"
}

// PUT /api/users/me   body → 200 (same shape as above)
{ "displayName": "<name>", "phoneNumber": "<phone>" }
// `role`, `email`, `id`, `entraObjectId` in the body are IGNORED (never bound).
// Use a dedicated request DTO with only the two mutable fields — do NOT bind the
// entity directly (mass-assignment / privilege escalation).

// GET /api/users      → 200  [ { …same shape… }, … ]

// PATCH /api/users/{id}/role   body → 200 (updated user)
{ "role": "Admin" }              // 400 if not exactly "User" or "Admin"
```

**Status codes / rules:**

* `401` — missing, expired, malformed, wrong-audience, wrong-issuer, wrong-tenant
  token, or a validated token with no usable `oid`. Includes the standard
  `WWW-Authenticate: Bearer` header.
* `403` — authenticated but **role or scope** insufficient: a `User` calling
  `GET /api/users`, or any caller whose token lacks `scp = Todos.ReadWrite`
  (16.7.2a). **The response body must not reveal whether the resource exists.**
* `503` — the role could not be read from PostgreSQL (fail closed, 16.7.6). Never
  degrade to "assume `User`", and categorically never to "assume `Admin`".
* `PATCH /api/users/{id}/role` guards:
  * `409 Conflict` if the caller targets **their own** row with `"User"`
    (self-demotion → instant lockout of the only admin during a demo).
  * `409 Conflict` if the change would leave **zero** `Admin` rows.
  * `404` if `{id}` does not exist.
  * Emit an `Information` audit log line: `"Role change: {ActorOid} set user {TargetId}
    from {OldRole} to {NewRole}."` — object IDs only, no PII.
* Every error uses `ProblemDetails`/`ValidationProblemDetails`, matching the existing
  `MalformedId` convention so the frontend's `extractErrorMessage` keeps working.

```ts
export const msalConfig = {
  auth: {
    clientId: import.meta.env.VITE_ENTRA_SPA_CLIENT_ID,
    authority: `https://${sub}.ciamlogin.com/${tenantId}`,
    knownAuthorities: [`${sub}.ciamlogin.com`],   // REQUIRED for ciamlogin hosts
    redirectUri: window.location.origin,
    navigateToLoginRequestUrl: true,
  },
  cache: { cacheLocation: 'sessionStorage', storeAuthStateInCookie: false },
};
export const loginRequest = { scopes: [import.meta.env.VITE_API_SCOPE] };
```

`knownAuthorities` is not optional — without it MSAL rejects the non-standard
`*.ciamlogin.com` authority. `sessionStorage` (not `localStorage`) is chosen to
shrink the XSS blast radius: tokens die with the tab. Tradeoff: a brand-new tab
re-runs `ssoSilent` (a hidden-iframe round trip against the IdP session cookie),
which is the intended behaviour anyway.

#### 16.9.2 Startup and login UX

1. `main.tsx` wraps `<App/>` in `<MsalProvider instance={pca}>` after
   `await pca.initialize()` and `await pca.handleRedirectPromise()`.
2. **Silent SSO first.** On load, if no account is cached, call
   `instance.ssoSilent(loginRequest)`. Render a neutral "Checking sign-in…" state
   while it runs.
3. On `InteractionRequiredAuthError` (or any failure) render `<LoginScreen>` with
   **two** actions:
   * **"Sign in / Sign up"** → `instance.loginRedirect(loginRequest)` → the
     Microsoft-hosted `SignUpSignIn` page, which itself shows the email + password
     form **and** a Google button, plus the "No account? Sign up" link.
   * **"Continue with Google"** →
     `instance.loginRedirect({ ...loginRequest, extraQueryParameters: { domain_hint: 'google.com' } })`.
     **Assumption A4 (16.16):** `domain_hint` is documented to route straight to the
     federated IdP; External ID user-flow behaviour must be **verified empirically**.
     If it does not bypass the picker, the button still lands on the hosted page
     where Google is one click away — **implement it so an unsupported hint degrades
     to the normal page, never to an error**.
4. Redirect (not popup) flows throughout: popups are blocked by default in many
   browsers and complicate the container/nginx setup for no benefit here.

#### 16.9.3 Calling the API

* A small `useAccessToken` hook wraps `instance.acquireTokenSilent({ ...loginRequest,
  account })`, catching `InteractionRequiredAuthError` → `acquireTokenRedirect`.
* `api.ts` stays framework-agnostic: add
  `export function configureApiAuth(getToken: () => Promise<string | null>)`, and in
  `request()` attach `Authorization: Bearer <token>` when a provider is configured.
  With no provider configured (existing unit tests) behaviour is unchanged — **no
  test rewrite churn**.
* On `401` from the API, clear local state and drop back to `<LoginScreen>` (the
  token was rejected; re-authenticate rather than retry-loop).

#### 16.9.4 Role-aware UI

* After authentication, fetch `GET /api/users/me` once and put it in a
  `UserContext` (`{ user, role, loading, error }`).
* Routes: `/` (todos, any authenticated user) and `/admin` (user list + promote/demote
  UI). `<RequireAdmin>` renders a "not authorized" panel and does not call admin APIs
  when `role !== 'Admin'`; the admin nav link is hidden.
* **State plainly in code comments and in `changes.md`: hiding the link is UX, not
  security.** A user who types `/admin` gets the panel but every admin API call still
  returns `403`, because the server re-derives the role from Postgres. The SPA must
  never gate on anything it can compute locally from a token claim.

### 16.10 Non-functional requirements

**Authentication / authorization**
* End users: OIDC/OAuth 2.0 authorization code + **PKCE** (public client, no secret),
  tokens validated on every API request against the external tenant's JWKS.
* Service-to-service (`todo-api` → Postgres / App Insights / ACR): **unchanged
  Entra managed identity** (§13/§14). No new service credential is introduced.
* Authorization data (`role`) is **always** re-derived server-side from Postgres.
* Application runtime secrets: **still zero.** The one new secret in the system (the
  Google client secret) is consumed by Entra External ID and custodied in Key Vault
  for humans (16.6).

**Transport security**
* All hops TLS: browser→ACA ingress, browser→`ciamlogin.com`, ACA→JWKS endpoint,
  `todo-api`→Postgres (`Ssl Mode=Require`). The only non-TLS endpoint anywhere in
  the design is the loopback dev redirect URI `http://localhost:5173/`.
* `RequireHttpsMetadata = true`. Metadata is fetched over TLS and cached by the
  handler with automatic refresh — no key material is stored by us.

**Token lifetime / session**
* Access token ~60–90 min (service default; do **not** try to shorten it in a
  custom token-lifetime policy this cycle).
* SPA refresh tokens obtained via the authorization-code flow in a browser are capped
  at **24 h** by the identity platform — after that the user re-authenticates
  (silently, if the IdP session cookie is still alive).
* The IdP's "Stay signed in?" prompt is default user-flow behaviour; suppressing it
  requires a Conditional Access session policy — **out of scope**.
* Role changes take effect on the **next request** (no token round trip needed),
  because the role is not in the token.

**CORS**
* `Cors__AllowedOrigins__0` (the `todo-web` FQDN) and `AllowAnyHeader()` already
  cover the new `Authorization` header. **No CORS config change is required** —
  but note the behavioural change: every API call is now a *non-simple* request, so
  the browser issues an `OPTIONS` preflight for each distinct path/method. `UseCors`
  must stay **before** `UseAuthentication`/`UseAuthorization` (16.7.6) so preflights
  are answered without a token, and so `401`/`403` responses carry CORS headers.
* Do **not** add `AllowCredentials()` — the token travels in a header, not a cookie.
* Keep the origin allow-list exact; never `AllowAnyOrigin()`.

**Scaling / performance**
* `todo-api` stays 0–3 replicas, 0.25 vCPU / 0.5 GiB. Every authenticated request now
  adds **one indexed single-row `SELECT`** on `users` (plus, once per user ever, one
  `INSERT`). At demo scale this is noise; it is traced automatically by the existing
  Npgsql OTel instrumentation (§12), so the cost is measurable in App Insights if it
  ever matters. Optimisation lever, if needed: the short-TTL role cache (16.7.3).
* Scale-to-zero still applies: the first request after a cold start additionally pays
  the OIDC metadata fetch (~1 round trip, then cached per replica).

**Observability**
* Existing OTel/App Insights tracing covers the new endpoints and the `users` query
  for free. **Never** log tokens, `Authorization` headers, passwords, email or phone.
  Log the `oid` (a pseudonymous GUID) when a user must be identified in a log line.
* The `users` table holds **PII** (email, name, phone). Keep it out of traces and
  logs; do not add it to custom telemetry dimensions.

**Payment / cardholder data — none exists in this application (verified)**
* This is a Todo application. As of this cycle there is **no payment processing,
  no order/checkout flow, no cardholder data, no PAN/CVV, no payment-provider
  integration, and no payment-related endpoint or column anywhere** in the
  backend, frontend, database, or infrastructure. Verified 2026-08-12 against the
  full source tree and §1–§14 of this document. The PCI DSS guidance in the repo
  `README.md` describes the **pipeline's engineering standards** for projects that
  do process payments; it does not describe this application's current scope.
  Do not add payment-related tables, endpoints, or scope handling in this cycle —
  it is not requested and is out of scope (16.15).
* Consequently there is **no payment endpoint for §16 to protect**, and the two
  roles (`User`, `Admin`) carry **no payment-related meaning**. `Admin` grants
  exactly two things: `GET /api/users` and `PATCH /api/users/{id}/role`. Nothing
  else. It must not be treated as a general-purpose "elevated" role by any future
  feature.
* **Forward constraints if payments are ever added** (binding on the feature that
  adds them, so this design does not have to be retrofitted):
  1. Cardholder data must not be stored in `users` or `todos`, or in any column of
     `tododb`. Use a processor's hosted fields/tokenization so the backend only
     ever sees a token (README PCI guidance); full PAN/CVV/track data is never
     stored, even encrypted.
  2. `Admin` must **not** implicitly grant access to payment or cardholder data. A
     payment feature introduces its **own** authorization policy and its own
     server-side check, re-derived from Postgres exactly as 16.7.3 does — adding a
     third role, if needed, is a spec change (16.15).
  3. Every payment-related endpoint is authenticated by the fallback policy
     (16.7.3) plus an explicit, dedicated policy; `[AllowAnonymous]` is never
     acceptable on one (webhook callbacks would need a separately-specified,
     signature-verified path, not an anonymous carve-out).
  4. Payment-provider credentials are third-party secrets that cannot use Entra
     auth, so they follow the **§13.6 Key Vault pattern** (Container Apps Key
     Vault reference + `Key Vault Secrets User` on the Container App managed
     identity) — never a Container Apps raw secret, never a committed value. Note
     this is a *different* pattern from the custodial-only vault use in 16.6.
  5. Payment data must never enter logs or telemetry dimensions — the same
     discipline already required for `users` PII below.

**Availability / failure modes**
* If Postgres is unreachable, the claims transformation cannot determine a role. It
  must **fail closed** (`500`/`503`, no role claim) — never "assume User", and
  categorically never "assume Admin".
* If the external tenant's metadata endpoint is unreachable at cold start, token
  validation fails ⇒ `401`s. `/health` still returns 200, so ACA does not restart-loop.

**Cost:** External ID ≤50k MAU = **$0**; Key Vault ≈ **$0** (a few operations/year);
no compute/SKU change. **Total incremental cost ≈ $0/month**, consistent with the
demo posture (§11.9).

**Region:** external tenant in **United States**; Key Vault in **eastus**
(`rg-todo-demo`). ACA `eastus` and Postgres `centralus` unchanged — do not "fix" that
mismatch (§14.11).

```sql

update users set role = 'Admin', updated_at = now()
```

`PATCH /api/users/{id}/role`.

"first user is Admin" rule — each is a privilege-escalation path that outlives the
bootstrap.

### 16.16 Assumptions, risks and open questions

**Assumptions (implement against these; verify where marked):**
* **A1.** A new external tenant can be created in subscription `9ba6633f-…` — the
  Container Apps Environment quota that paused §15 is specific to ACA and does not
  apply here. *Verify at step 1; if a Tenant Creator/subscription-policy block
  appears, the 30-day trial tenant is the fallback for demo purposes.*
* **A2.** `oid` is present in every access token the user flow issues, and is stable
  across local and Google-federated accounts. *Verify by decoding a real token at
  jwt.ms for both account types.*
* **A3.** Attribute collection (phone) runs on the first **Google** sign-up, not just
  local sign-up. *Verify. If it does not, `phone_number` stays null until the user
  sets it via `PUT /api/users/me` — no code change needed.*
* **A4.** `domain_hint=google.com` routes straight to Google from an External ID user
  flow. *Verify. Must degrade to the normal hosted page, never to an error.*
* **A5.** `Microsoft.Identity.Web` accepts the External ID issuer/authority host
  mismatch out of the box. *Verify against a real token; remedy is explicit
  `ValidIssuers`, never disabled validation.*
* **A6.** The optional claims (`email`, `given_name`, `family_name`, extension phone)
  actually appear in the **access** token (not only the ID token). *Verify; if the
  access token lacks them, the profile fields are simply null until the user edits
  them — authorization is unaffected because it never depends on these claims.*
* **A7.** The existing `todo-api` managed identity's Postgres role can create the new
  table (it owns `public` per §14.7 Phase 4 grants), so startup `Migrate()` succeeds.
* **A8.** The External ID user flow issues the delegated permission as a
  space-separated **`scp`** claim (v2 tokens, `accessTokenAcceptedVersion = 2`), which
  is what `[RequiredScope]` reads. *Verify by decoding a real access token at jwt.ms.*
  If the claim were absent, every call would `403` — a **fail-closed** outcome, which
  is the correct direction; the remedy is to fix the app registration/user flow, never
  to remove the scope check (16.7.2a).

**Risks (must be reflected in `changes.md`):**
* **Breaking change / release window.** The moment the new backend is live, the
  *old* frontend image gets `401` on every call, and a new frontend against an old
  backend is equally broken. CD deploys backend → frontend in one run, so there is a
  short window of a broken app. Accepted for a demo; rollback is
  `az containerapp revision activate` on **both** apps (capture both revision names
  first).
* **Missing/incorrect auth env vars ⇒ the API fails to start** (by design, 16.7.1).
  Mitigated by applying the env vars imperatively before/with the deploy (16.12 item
  6) and by capturing the rollback revision.
* **PII arrives in the database for the first time** (email, name, phone). No
  encryption-at-rest change is needed (Postgres Flexible Server encrypts at rest by
  default), but logging discipline is now a real requirement, not a nicety.
* **A single Admin.** Losing access to the bootstrap account means editing the DB
  again. The self-demotion and last-admin guards (16.8) reduce, not eliminate, this.
* **External tenant lifecycle.** Deleting a `ciamDirectories` resource is known to be
  awkward; create it once, deliberately, with the intended name/region (region is
  immutable).

**Open questions (do not block implementation):**
* **Q1.** Should the role lookup be cached (30–60 s) once real usage exists?
  *Recommendation: no for now; revisit only with trace evidence, and document the
  revocation-delay tradeoff if adopted.*
* **Q2.** Should `todos` eventually become per-user? *Recommendation: a separate
  cycle; it is a data-model + migration change, not an auth change.*
* **Q3.** One external tenant or two when §15 lands? *Recommendation: one (16.14).*
* **Q4.** Should `last_login_at` be tracked? *Recommendation: no — it converts every
  authenticated request into a write. If needed, do it as a coarse (daily) update.*
* **Q5.** Should the Google client secret also be mirrored anywhere for DR?
  *Recommendation: no. It is re-issuable from Google Cloud in minutes; Key Vault
  custody plus soft-delete is enough.*

### 16.17 Acceptance criteria (maps 1:1 to the requested verification)

1. **Self-registration works.** A new visitor can sign up with email + password,
   supplying name and phone on the sign-up page, and lands back in the SPA
   authenticated.
2. **Google sign-in works.** "Continue with Google" (or the Google button on the
   hosted page) completes sign-up/sign-in with a Google account and lands back
   authenticated.
3. **Profile auto-provisioned.** After the first sign-in of either kind, `users`
   contains exactly one row for that person, keyed by `oid`, with `role = 'User'`;
   a second sign-in creates no duplicate.
4. **Unauthenticated calls are rejected.** `curl https://<api-fqdn>/api/todos`
   without a token ⇒ `401`. `curl https://<api-fqdn>/health` ⇒ `200`.
5. **A `User` is blocked from admin functionality.** `GET /api/users` and
   `PATCH /api/users/{id}/role` ⇒ `403` for a `User` token, and `/admin` in the SPA
   shows the not-authorized panel (link hidden).
6. **Bootstrap promotion works.** After the manual `UPDATE users SET role='Admin'`,
   the same user's **next** request is admin-authorized with **no re-login**
   (proves the role is re-derived server-side, not carried in the token).
7. **The Admin can reach admin pages/endpoints.** `/admin` renders the user list;
   `GET /api/users` ⇒ `200`; `PATCH /api/users/{id}/role` promotes another user, who
   gains access on their next request.
8. **Escalation attempts fail.** A forged/modified role claim in the token, a `role`
   field in a `PUT /api/users/me` body, and a token issued for a different audience
   (the SPA's ID token) are all rejected — `403`/ignored/`401` respectively.
9. **No secrets anywhere.** `todo-api` has **zero** Container Apps secrets; the only
   Key Vault secret is `google-oauth-client-secret`, readable by a human role
   assignment only; no secret appears in git, in `appsettings*.json`, in workflow
   files, or in this document.
